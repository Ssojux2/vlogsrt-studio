# 초안 내보내기 거부 — 선언 창 판정의 거짓 거부 (계획, 2026-11-12)

상태: **구현됨**(2026-11-12, 권장안 ①-a · ② · ③ 사용자 승인 — D113 · W-62).

## 1. 증상

「추천만 이어붙여 내보내기」가 원본 8개를 이유로 초안 전체를 만들지 않았다.

```
지난 내보내기 실패 — 초안을 만들지 않았다 — 원본 8개:
IMG_8987.MOV: 렌더할 수 없다 — 패킷 증거(19/5초)가 선언 창(0~3798333/1000000초)을 넘는다 — 입력 탐색 창이 그 구간을 잃는다 / …
```

거부 자리: `preprocess._raw_timeline_failures`(`vlogsrt/preprocess.py:3307`)의 선언 창 판정 →
`render_part_failures` → `render_export._gather`(`vlogsrt/project/raw/render_export.py:223`).
같은 판정이 `_assert_raw_supported`를 거쳐 **구간 추출(`extract_raw_clip`, 서비스의
`run_segment_extraction`)도 막는다** — 이 8개는 구간 추출도 같은 문구로 실패한다.

## 2. 실측 (namdang 169개, 무료 ffprobe)

스크립트: `probe_raw_media` + `probe_extraction_clock` + `render_part_failures`를 원본마다 돌렸다.
모두 tb 1/600 · 30fps · 시작 0 · 균일 격자(`uniform`)다. 「넘침」은 (패킷 증거 끝 − 적힌 선언 끝) / 틱.

| 시계 | 넘침(틱) | 개수 | 판정 |
|---|---|---|---|
| uniform | 1 (적힌 선언이 정확) | 10 | 통과 |
| uniform | 4999/5000 (µs 반올림이 위로) | 10 | 통과 |
| uniform | **5001/5000 (µs 반올림이 아래로)** | **7** | **거부** |
| uniform | **12** | **1** (IMG_1071) | **거부** |
| uniform | ≤ 0 · 1/5000 | 44 | 통과 |
| snap | 5001/5000 포함 전부 | 97 | 통과 |

거부 8개: IMG_8987 · IMG_8991 · IMG_1070 · IMG_1154 · IMG_1164 · IMG_1170 · IMG_1202(원인 A) · IMG_1071(원인 B).

## 3. 근본 원인

### 원인 A — 적힌 선언의 µs 반올림이 판정을 정한다 (7개)

- 애플 MOV는 마지막 프레임을 19틱으로 선언한다: IMG_8987 영상 트랙 `duration_ts` 2279 · 마지막
  패킷 pts 2260 + 20 = 2280. **참 넘침은 정확히 한 틱**이고, 균일 시계의 허용(`_declared_window_slack`
  = 한 틱)이 원래 받는 모양이다.
- 그런데 판정은 format duration을 **ffprobe가 µs로 적은 값**과 비교한다. 2279/600 = 3.7983333…초가
  3.798333초로 적혀 참값보다 1/3 µs 이르다 → 넘침이 한 틱 + 1/3 µs가 되어 거부된다.
- 반올림은 **가장 가까운 µs**다(IMG_9006: 13/6 = 2.1666666…가 2.166667로 위로 적혔다). 그래서 같은
  모양의 균일 원본 27개가 반올림 방향만으로 20 통과 · 7 거부로 갈린다.
- 이건 IMG_8863에서 이미 잡은 버그다(`_declared_window_slack` docstring) — 그때 **snap 시계에만**
  µs 눈금 몫을 붙이고 균일 시계는 「판정 바이트 그대로」로 남겼다. 그 결정이 바로 이 7개를 막는다.
  같은 넘침의 snap 원본 18개는 통과한다.

### 원인 B — 짧은 마지막 패킷을 명목 길이로 잰다 (IMG_1071)

- IMG_1071(`.mov` 소문자, 사진 앱에서 다듬은 클립)의 마지막 패킷은 pts 1780 · **길이 8틱**이고 트랙
  선언 끝은 1788틱 = 2.98초다. 마지막 패킷은 선언 창 **안에서 시작해 정확히 창 끝에서 끝난다**.
- 균일 시계의 패킷 증거 끝(`_packet_evidence_end`)은 `exact_end` = 원점 + 90 × 1/30 = 3.0초(명목)라
  12틱 넘친 것처럼 보인다. 시계 조사(`packet=pts`)가 패킷 길이를 읽지 않아 실제 끝을 모른다.

### 원인 C (구조) — 원본 하나가 초안 전체를 막는다

`render_export._gather_sources`는 문제를 다 모아 **한 번에 거부**한다. VFR·map 원본은 계획이 빼고
보고서에 남기는데(D68 정신), `render_part_failures` 거부만은 초안 전체를 멈춘다. A·B를 고쳐도 다음에
다른 이유로 원본 하나가 거부되면 같은 일이 난다.

## 4. 판정을 풀어도 되는 증거

판정의 근거는 「선언 창보다 먼 패킷은 입력 `-ss` 창이 잃는다」(1.25초 밀린 파일에서 90 중 33프레임)다.
이 8개는 그 모양이 아니다 — 모든 패킷이 창 **안에서 시작**한다. 실측:

- `ffmpeg -ss X -i …` framemd5: IMG_8987 114/114 · IMG_1071 90/90 · 끝 근처 탐색에서도 기대한 프레임 수.
- **실제 argv**(판정만 우회한 스크래치 스크립트, `render_part`·`extract_raw_clip` 그대로): IMG_8987 ·
  IMG_1071 · IMG_1202 각각 마지막 20프레임 조각과 전체 조각이 **렌더 검증(`_verify_render_part`)과
  추출 검증(프레임 수·격자·디코드)을 모두 통과**했다. 추출 경로는 `tpad` 채움이 없어 마지막 프레임을
  실제로 읽었다는 증거다.

## 5. 수정 계획

### 5-1. 원인 A — 균일 시계 허용에 µs 반올림 반 눈금 (결정 ①)

`_declared_window_slack`의 균일 가지를 `time_base + ½ µs`로 넓힌다. 근거: 적힌 선언은 참값의
가장 가까운 µs이므로 참값과 **½ µs 이하**로만 다르다 — 그 몫은 참 선언의 몫이지 넘침이 아니다.

- **권장 ①-a (½ µs)**: 고정된 시험 `test_a_uniform_clock_keeps_the_one_tick_window`(한 틱 + **1 µs** 넘침
  → 거부)가 **그대로 통과**한다. 7개는 넘침이 한 틱 + 1/3 µs라 받는다. 판정이 바뀌는 범위는 정확히
  「한 틱 + (0, ½ µs]」 띠 — 반올림 잔차뿐이다.
- 대안 ①-b (snap과 같은 2 µs): 규칙이 snap과 같아 단순하지만 위 시험의 기대값을 뒤집는다(CLAUDE.md상
  기대값 수정 — 사람 승인 필요). 권하지 않는다.
- snap·map 가지는 그대로.

### 5-2. 원인 B — 균일 시계의 패킷 증거 끝을 실제 마지막 패킷 길이로 (결정 ②)

- `probe_extraction_clock`의 조사에 `packet=pts,duration`을 싣고 `RawVideoClock`에 마지막 패킷 길이 칸
  (`last_packet_ticks: int = 0`, 0 = 모름)을 더한다.
- `_packet_evidence_end`의 균일 가지: 길이를 알면 `last_pts·tb + min(frame_duration, last_packet_ticks·tb)`,
  모르면 지금처럼 `exact_end`. **줄이기만** 한다 — 명목보다 긴 마지막 패킷이 판정을 느슨하게 하지 않는다.
- IMG_1071: 1780 + 8 = 1788틱 = 선언 끝 → 넘침 0으로 통과. 그 밖의 168개는 마지막 패킷이 20틱이라
  값이 그대로다(회귀 표로 확인).
- 새 칸은 지문·캐시 열쇠·`frames_fingerprint`·검토 머리 시계 비교에 넣지 않는다 — 착수 때
  `RawVideoClock`을 직렬화·비교하는 자리(`asdict`·`==`·`_require_same_clock`)를 먼저 전수 확인한다.
  시험의 가짜 ffprobe JSON에 `duration`이 없으면 0(모름)이라 기존 시험은 그대로다.
- 대안 ②-b: 균일도 map처럼 「마지막 패킷이 창 안에서 시작하는가」만 본다. 한 줄이지만 고정된 시험
  둘(`test_a_uniform_clock_keeps_the_one_tick_window`·`test_the_window_guard_still_refuses_a_packet_beyond_the_declaration`)을
  뒤집고 fail-closed 폭을 한 프레임까지 넓힌다. 권하지 않는다.
- 남는 사실(고치지 않음): IMG_1071의 초안·Final Cut 길이는 명목 3.0초이고 원본은 2.98초다 —
  마지막 프레임을 1/30초 쥐고 소리는 `apad`로 0.02초 침묵을 채운다. 이미 Final Cut 보내기가 그렇게
  다룬다.

### 5-3. 원인 C — 렌더할 수 없는 원본은 빼고 알린다 (결정 ③, 제품 판단)

- 권장: `_gather`의 `render_part_failures` 거부를 map·VFR과 같은 「빼고 보고서에 이름」 길로 옮긴다 —
  `render_report.json`과 결과 카드 경고에 원본 이름·까닭을 남기고, 나머지로 초안을 만든다(D68 ·
  D100 §5b의 「막지 않고 알린다」와 같은 선). 원본을 읽지 못함·바뀜(`_require_unchanged`)·시계 불일치는
  지금처럼 거부한다 — 그건 원본이 아니라 작업공간 상태의 문제다.
- 대안: 지금처럼 전부 거부(엄격). 5-1·5-2만으로도 이번 8개는 풀린다.

### 5-4. 시험 (먼저 쓴다)

- `tests/raw/test_grid_conform.py`: IMG_8987 모양(tb 1/600 · 114패킷 · 트랙 2279틱 · format 3.798333초)이

- IMG_1071 모양(마지막 패킷 길이 8틱 · 선언 1788틱) 통과 / 마지막 패킷이 선언 끝 너머에서 **시작**하면 거부.
- 마지막 패킷 길이가 명목보다 길거나 없으면 판정이 지금과 같다.
- (③을 고르면) `render_export` 시험: 거부 원본 하나가 있는 작업공간에서 초안이 나머지로 만들어지고

## 6. 하지 않는 것

- 선언 창 판정을 끄지 않는다 — 창 밖에서 **시작하는** 패킷은 계속 막는다.
- snap·map 판정, 균일 원본의 시계·추출 argv·지문은 바꾸지 않는다.
- 임계값 표(CLAUDE.md)에 새 조정값을 만들지 않는다 — ½ µs는 ffprobe 표기의 기하 근거다.
