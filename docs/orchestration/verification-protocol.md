# 검증 프로토콜 — 무거운 일은 GLM, 계획과 방향은 Fable, 진행은 Opus

2026-09-10에 사용자가 역할을 이렇게 못 박았다.

| 역할 | 모델 | 자리 |
|---|---|---|
| 계획 수립·오케스트레이션·머지 게이트 | Opus 5 | 이 코디네이터 세션 |
| 구현 | `claude-glm` `glm-5.3[1m]` max | 태스크별 fresh 워커 |
| **검증 — 토큰 무거운 부분** | `claude-glm` `glm-5.3[1m]` max | **구현자와 다른 fresh 워커** |
| **계획·방향성의 자세한 검토** | **Fable 5.1 high** | **상시 역할. 다툼이 있을 때만이 아니다** |

Orca가 오케스트레이션을 담당한다 — 이 저장소에 `run_phase.sh`나 `--director` 플래그는 없다.

## 세 층이 서로 다른 것을 본다

**GLM 검증자 — "구현이 브리프대로인가"**
브리프를 기준으로 diff를 대조한다. 브리프가 틀렸으면 구조적으로 못 잡는다.

**Fable 5.1 — "브리프와 방향이 애초에 옳은가"**
계약·인터페이스·페이즈 순서·명세 정합성을 본다. GLM 검증자가 볼 수 없는 층이다.
P4-04가 정확히 이 층에서 걸렸다: 게이트는 전부 초록이었고 구현은 브리프대로였는데,
**내가 넘긴 계약 자체**가 `project_boundaries`에서 정확한 닻에 손이 닿지 않게 만들어
구현자가 시각을 유도하도록 몰았다. Fable은 동시에 내 주장 셋 중 **둘을 반박**했다 —
방향 검토는 승인 도장이 아니라 양방향이다.

**Opus 5 — 진행과 머지**
태스크를 쪼개고, 브리프를 쓰고, 워커를 붙이고, 두 보고서를 증거로 받아 머지를 결정하고,
통합 `make check`를 돌린다(싸다). 위험 주장 한둘만 직접 확인한다.

## 왜 검증자가 구현자와 달라야 하는가

이 세션에서 GLM 자기 보고가 **두 번 부정확했다**. 게이트는 매번 진짜로 초록이었지만
보고서가 틀렸다.

- P5-05b: 불변식을 "15/15"로 보고했으나 실제로는 19개 전부 통과였다.
- P4-04: 유도한 이동량을 "정확히 유도한다"고 적어 결함을 정상으로 서술했다.

둘 다 보고서를 받아 적었으면 놓쳤다. **구현자는 자기 일을 검증하지 않는다.**

## GLM 검증자가 하는 일 (토큰이 무거운 전부)

1. 게이트 전부를 직접 돌리고 **출력 그대로** 싣는다. 요약 줄을 믿지 않는다 —
   불변식은 `[OK]` 줄을 **세어** 숫자로 보고한다.
2. 브리프의 Contract 항목을 **한 줄씩** diff에 대조한다. 항목마다
   `충족 / 미충족 / 해당없음`과 **근거가 되는 파일:줄**을 적는다.
3. 적대적 재현을 직접 짠다 — 계약이 막겠다고 한 것을 실제로 시도해 막히는지 본다.
   동시에 **성공 경로가 여전히 도달 가능한지** 함께 증명한다. 그게 없으면
   "전부 막혔다"가 "파서가 통째로 망가졌다"와 구별되지 않는다.
4. 신원·캐시 키가 바뀌면 안 되는 변경이면, 박힌 다이제스트를 **변경 전 커밋**에
   임시 워크트리를 만들어 돌려 순환 논증이 아님을 증명한다.
5. 구현자 보고서의 **모든 수치 주장을 재측정**하고 어긋나면 그 자리에 적는다.
6. 소유 파일 밖 변경, `.env.example` 오염, 네트워크 호출 흔적을 확인한다.

**검증자는 제품 코드를 고치지 않는다.** 발견만 적는다.

## Fable 5.1이 하는 일 (계획과 방향)

페이즈 시작 전 **브리프 검토**, 그리고 후보가 나온 뒤 **방향 검토**를 맡는다.

1. 브리프의 계약이 `docs/plans/2026-09-08-final-cut-project.md`와 어긋나지 않는가.
2. 시그니처가 필요한 정보를 실제로 나르는가 — **P4-04의 실패 모드**. 소비자가
   상류의 정확한 값에 손이 닿는지 확인한다. 닿지 않으면 구현자는 유도할 수밖에 없다.
3. 페이즈 순서와 의존성이 옳은가. 선행 태스크 없이 시작하는 것이 있는가.
4. 이 태스크가 다음 페이즈에 물려줄 인터페이스가 하류를 막지 않는가.
5. Opus의 주장을 **반박해도 된다.** 근거 없는 동의는 검토가 아니다.
6. 읽기 전용이다 — 코드를 고치지 않고 판정과 최소 수정 명세만 낸다.

## 보고 형식

GLM 검증자:
```
VERDICT: ACCEPT | ACCEPT_WITH_FINDINGS | REJECT
게이트: <명령마다 실제 출력 숫자. 불변식은 센 값>
계약 대조: <항목별 충족/미충족 + 파일:줄>
적대적 재현: <시도, 막힘 여부, 성공 경로 도달 가능 증명>
구현자 수치 재측정: <일치/불일치>
범위: <git diff --stat, 허용 파일 밖 변경 여부>
발견: <심각도와 함께. 없으면 "없음">
```

Fable 5.1:
```
방향 판정: SOUND | SOUND_WITH_CONCERNS | REDIRECT
계약 대 명세: <어긋난 곳>
시그니처 충분성: <소비자가 상류 정확값에 닿는가>
의존성·순서: <문제>
하류 영향: <다음 페이즈를 막는가>
Opus 주장 검토: <확인 / 반박 + 근거>
최소 수정 명세: <필요하면>
```

Opus는 두 보고서를 **증거로** 받지 결론으로 받지 않는다.
