### Source observations and implementation order

1. `commands.py` already writes atomic result/candidate files and an attempt journal, but has no durable work-progress message. Add a strict Python/Swift progress contract with job/input/estimate/attempt identity, stage, status and optional known completed/total values. Use actual counts; preparation/audio stages may remain indeterminate. A stage count is not a whole-job percentage. Reject malformed identity, negative/bool/noninteger counts, completed greater than total, unknown enums and impossible terminal combinations. Preserve existing protocol readers/fixtures and legacy conservative behavior.
2. Publish atomic snapshots from actual analysis boundaries: started/preparation/audio, planned vision windows and each completed window, final publication or failure/cancellation. Include replay and zero-window behavior without falsely claiming paid success. Do not mark successful completion before the attempt/result/candidates are durable and coherent. Catch failures without masking the original exit or storing raw secrets. No per-source runner refactor is required merely to manufacture fine-grained counts.
3. `vlogsrt-engine.py` currently copies workspace results to job root only after `_run_operation`; `EngineSessionRunner` copies external development jobs only after `executor.run`. Solve both real transport hops so progress is observable DURING the single invocation. Prefer a narrow progress-only atomic publication/relay during execution; do not publish candidate/roughcut success artifacts early. Keep existing final sync/import gates. Bundled and development paths both work; cancelled/stale/replaced requests stop relay. Teardown must join/cancel its timer/task, preserve original exit and never launch another engine. Any optional sink must be invocation-owned and validated; do not accept arbitrary unbound global output paths.
4. Add a testable core refresh/session model consumed by the actual `WorkflowViewController`. A bounded polling cadence reads durable state only; it neither calls the engine nor approves paid execution. Bind callbacks to the current job/request generation; ignore old open callbacks, stale attempts/revisions and cancelled jobs. Observe estimate-only completion as a cost-approval-ready state, without auto-approving or silently launching paid work. Do not interpret a terminal progress snapshot as trustworthy candidate content before existing result/attempt/estimate validation succeeds. Handle the small final-publication gap with bounded reads, not a stuck timer or false unknown success. Absent/corrupt/legacy data stays conservative and does not reexecute anything.
5. Wire start/stop to actual URL request/open failure, view appear/disappear, active project change, job replacement and cancellation. Ensure indefinite absent progress is bounded and explains manual recovery without auto-reexecution. Starting/replacing monitoring cancels the old task. The timer must not retain a closed view or update another job. Analysis and roughcut buttons reflect the actual pending/review state.
6. Preserve checkbox choices when reloading the SAME accepted result/candidate revision, including temporary unavailable snapshots; reset on a genuinely NEW revision or job. Selection state has one clear owner, with tests for repeated refresh and identical candidate IDs in a new revision. Preserve partial-error warnings and safe-candidate gating. No redesign of review/caption/import features.
