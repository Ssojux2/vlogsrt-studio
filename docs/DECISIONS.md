## D1. `docs/PLAN.md` 없이 구현했다

`CLAUDE.md`와 `TASKS.md`가 `docs/PLAN.md`의 섹션을 참조하지만 그 파일은 저장소에 없다.

**영향**: PLAN에만 적혀 있었을 세부 규칙(예: §6.6 고아 처리의 정확한 절차,
§6.8 이상치 검사 항목 전체 목록)은 이 문서의 판단으로 대체했다. 아래 D4, D6이 그것이다.
PLAN이 나타나면 이 세 항목을 대조해야 한다.

## D3. `Cue.text`는 속성, `text_raw`는 두지 않았다

## D4. 고아 처리는 "전체 골격 재사상"으로 풀었다

**문제**: `build_w`는 `verdict != ok` 세그먼트를 뺀다. 그러면 그 시간대의 gpt 텍스트는
정렬에서 `insert` 블록이 되어 이웃 큐에 통째로 흡수된다. 텍스트는 살아남지만 **엉뚱한 시각에 뜬다.**

**해법**: `rescue_orphans`가 제외 세그먼트를 **포함한** W로 한 번 더 정렬한다
(`build_w(spine, include_all=True)`). 제외 세그먼트가 차지한 A 구간을 잘라내
고아 큐로 만들고, 그 텍스트가 이웃 큐에 흡수돼 있으면 거기서 뺀다(중복 방지).

고아 큐의 시각은 제외 세그먼트 자신의 `start`/`end`다 — 추정이지만 근거 있는 추정이다.
`conf`는 `orphan_conf_max`(0.30)로 고정하고 `time_estimated` 플래그를 단다.

**한계**: 이웃 큐에서 텍스트를 뺄 때 부분 문자열 일치를 쓴다. 같은 문장이 두 번 나오면
엉뚱한 쪽에서 뺄 수 있다. `tests/test_mapping.py::test_orphan`이 중복 없음을 검사한다.

## D5. `insert` 블록의 절단점은 `j1`로 보낸다

`map_position`이 `insert`/`delete` 블록 안에 떨어지면 `j1`을 돌려준다.
다만 자모 단위 정렬에서는 `insert` 블록이 음절 중간에 생기는 일이 흔해,
실제 결과는 어느 쪽으로든 한 음절 이내에서 갈린다. 그 뒤 어절 스냅이 정리한다.

`tests/fixtures/synthetic/map_cases.json`이 16개 케이스의 결과를 못 박아 뒀다.
이 값이 바뀌면 정렬 동작이 바뀐 것이다.

## D6. 이상치 검사 항목 (PLAN §6.8 대체)

| 수준 | 코드 | 뜻 |
|---|---|---|
| ERR | `bad_range` | `end <= start` |
| ERR | `empty_text` | 텍스트 없음 |
| ERR | `overlap` | 앞 큐와 겹침 |
| ERR | `too_many_lines` | `max_lines` 초과 |
| ERR | `unknown_seg` | 골격에 없는 `seg_id` |
| WARN | `line_too_wide` `too_short` `too_long` `cps` `tight_gap` `low_conf` `no_origin` `out_of_spine` | 기록만 |
| INFO | `orphan` `flag:*` | 참고 |

`ERR`은 파이프라인이 고친다(시간 보정 → 충돌 해소 → 빈 큐 제거).
정상 실행에서 `ERR`은 0이어야 한다.

## D12. TASKS.md §T3.1의 gpt 호출 파라미터가 틀렸다 (실측)

TASKS.md는 `gpt-transcribe` 호출에 `language`와 `languages`를 **둘 다** 넘기라고
적어두었다. 실제 API는 400을 돌려준다.

```
The 'language' and 'languages' parameters cannot be used together.
```

여러 언어를 알려주는 쪽이 이 프로젝트의 의도(한국어 브이로그 + 영어 상호명)라
`languages`를 택했고, `extra_languages`가 비어 있을 때만 단일 `language`로 떨어진다.
**임계값이 아니라 API 계약이라 고쳤다.** 근거는 실측 응답이고
`tests/test_transcribe.py`가 조합을 못 박는다.

### 곁들여 드러난 것: 반쪽 녹화

whisper는 성공하고 gpt가 이 400으로 죽었다. `record_fixtures`가 dict 리터럴
순서대로 whisper를 먼저 저장했기 때문에 `*.whisper.json` 만 남았다. 그런데

- `has_fixture()` 가 whisper만 확인해서 "녹화됨"으로 판정 → 녹화를 건너뛰고
  곧바로 없는 gpt 픽스처를 찾다가 실패
- 다시 녹화하면 성공한 whisper까지 재결제 (77분이면 약 $0.46)

둘 다 고쳤다. `has_fixture()` 는 두 모델 응답이 **모두** 있어야 참이고,
`record_fixtures(reuse_existing=True)` 는 이미 있는 응답을 다시 부르지 않는다.

## D11. gradio UI는 패키지 **밖**에 둔다

불변 규칙 7은 의존성을 `openai`, `tomli-w`, `rich` 셋으로 못 박는다. 웹 UI 요청이
들어왔을 때 선택지는 셋이었다.

1. `vlogsrt/`에 gradio를 넣는다 → 규칙 7 위반. 핵심 파이프라인이 무거워지고,
   `make check`가 UI 설치 여부에 흔들린다
2. UI를 만들지 않는다 → 사용자의 실제 요구를 거절하는 것
3. **UI를 `ui/`에 두고 선택적 extra로 만든다** ← 선택

`ui/`는 vlogsrt를 라이브러리로 쓰고, `vlogsrt/`는 gradio를 모른다.
`[project.dependencies]`는 그대로 3개이며, gradio는 `[project.optional-dependencies] ui`에 있다.
`scripts/check_invariants.py`가 `vlogsrt/`의 gradio import를 금지 목록으로 막는다.

`ui/service.py`(순수 로직)와 `ui/app.py`(화면)를 가른 이유도 같다.
service는 gradio를 import하지 않아 UI 없이도 테스트가 돈다.

### 화면은 세 개로 줄였다

처음에는 슬라이더·탭·미리보기·재조판까지 넣었는데, 쓰는 사람이 원한 것은
**경로 입력 · 실행 로그 · SRT** 셋뿐이었다. 나머지는 걷어냈다.
조판 조정은 `vlogsrt redo`가 이미 더 잘한다 — 화면에 두 번 만들 이유가 없다.
`make_subtitles()`는 예외를 던지지 않고 전부 로그 문자열로 돌려준다.
빨간 토스트보다 로그 한 칸이 읽기 쉽다.

### 파일 고르기는 서버 쪽 네이티브 대화상자로 간다

세 번 갈아탔다. 기록해 둘 값어치가 있다.

1. `gr.FileExplorer` — **파일이 하나도 안 보였다.** glob을 `**/*.{mp4,mov,...}` 로
   줬는데 gradio는 `fnmatch`로 매칭하고, `fnmatch`는 중괄호 확장을 지원하지 않는다.
2. `gr.File` — OS 대화상자는 열리지만 브라우저가 **실제 경로를 안 준다**(`C:\fakepath\...`).
   파일이 통째로 서버로 올라오고(복사), 원본 폴더를 알 수 없어 SRT를 옆에 못 둔다.
3. **`osascript`로 서버에서 대화상자를 연다** ← 현재.
   서버가 곧 이 컴퓨터라서 가능한 방법이다. 진짜 경로가 오고, 복사가 없고,
   큰 영상도 즉시 시작된다.

대가: macOS 전용이고, `--share` 로 남에게 열어주면 대화상자가 서버 컴퓨터에 뜬다.
개인 도구라 받아들일 만하다. 다른 OS에서는 경로 직접 입력으로 안내한다.

AppleScript를 문자열로 만들다 보니 조립 실수가 났다 — 플레이스홀더를 `{TYPES}` 로
두는 바람에 `.replace()` 가 중괄호까지 먹어 `of type "mp4", ...` 가 됐다.
문자열 검사로는 안 잡혀서, 테스트가 `osacompile` 로 **실제 컴파일**해 본다.

### 최종 SRT는 원본 영상 옆에

편집 프로그램에 넣을 때 영상과 같은 폴더에 있는 편이 손이 덜 간다.
SRT만 옆에 두고, 검토용·리포트·`trace.json`은 `out/<회차>/`에 남긴다 —
사람 폴더에 작업 부산물을 흘리지 않기 위해서다.

업로드본은 원본 폴더를 알 수 없어 `out/`에 둔다. 판정은 gradio 임시 폴더
아래인지로 하는데, macOS에서 `gettempdir()`는 `/var/folders/...`를 주고 실제
경로는 `/private/var/folders/...`라 **양쪽 다 resolve해야** 한다.
이걸 빠뜨렸을 때 SRT가 조용히 임시 폴더로 들어갔다.

### gradio 6에서 부딪힌 것

- `theme`/`css`가 `Blocks()`에서 `launch()`로 옮겨졌다
- `launch(show_api=...)`가 사라졌다
- `gr.Video`의 `postprocess`가 더 이상 `(video, subtitle)` 튜플을 받지 않는다
  (독스트링에는 남아 있지만 코드에는 없다). `gr.update(subtitles=경로)`도
  경로 문자열을 그대로 보내 프런트가 못 읽는다. **컴포넌트 인스턴스를 돌려주면**
  생성자가 SRT를 VTT로 바꿔 FileData로 감싸준다 — 그 경로를 썼다
- `no_site_packages = true`를 켰다. ui extra가 numpy를 끌어오는데 numpy 스텁이
  3.12 문법이라 `python_version = "3.11"` 설정으로는 파싱조차 실패했다.
  이제 mypy 결과가 무엇이 설치돼 있는지에 흔들리지 않는다

## D13 — 자막 어긋남의 원인은 절단이 아니라 whisper 전사였다

77분 영상(`fr_day_1_2_fhd`)의 SRT가 소리와 맞지 않는다는 신고. 첫 의심은
"모델에 들어가는 클립이 잘못 잘렸다"였다. **아니었다.** 실측으로 갈랐다.

절단 경로는 이상이 없다:

| 검사 | 결과 |
|---|---|
| ffmpeg `-i` 뒤 `-ss/-to` 출력 탐색 | 마커 오디오로 확인, 정확 |
| loudnorm 통과 후 타임라인 | 300초에서 오차 **0.000초** |
| 4조각 분할 후 로컬시각+오프셋 | 전 조각 일치 |
| 실제 청크 ↔ 전체 오디오 포락선 | 상관 0.9999 / 1.0000, 지연 **0.0초** |
| 영상 길이 ↔ 오디오 길이 | 차이 0.094초 |
| 골격 시각 ↔ 실제 소리(F1 최대화) | 최적 시프트 **0.0초** (단봉) |

원인은 whisper-1의 디코딩 붕괴다:

- **프롬프트 오염.** `vlogsrt.toml`의 `prompt`가 메타 지시문이었다
  (`"브이로그 내레이션입니다. 구어체 한국어이며 …"`). whisper는 `prompt`를 지시가
  아니라 **직전 자막 텍스트**로 보고 이어 쓴다. 그 결과 11.9초부터 582.3초까지
  570초 동안 `'구어체 한국어에서 한국어 자막을 사용합니다.'`를 103회 반복했다.
- **반복 루프.** 총 10구간 1134초 = 영상의 **24.7%**가 같은 문장 반복이다.
  청크가 38분씩이라 디코더가 뒤로 갈수록 무너진다(청크1 실패는 전부 후반부).
- **0길이 세그먼트** 1931개 중 452개(23.4%).

여기서 파이프라인의 구조적 약점이 드러났다:

1. `compression_ratio`는 **세그먼트 안쪽** 반복만 본다. whisper가 반복을 세그먼트
   단위로 쪼개면 각각은 압축률 0.97로 정상이라 그대로 통과한다. → `vlogsrt/loops.py`
2. 환청 판정으로 빠진 구간은 `rescue_orphans`가 되살리는데, 반복 구간은 정렬이
   무너져 **정본 텍스트 570초분이 큐 하나에 몰린다**. 0.77초 큐에 773자가 나온
   이유다. 뒤따르는 세그먼트는 0자가 되어 202개가 사라졌다.
3. 결과: SRT가 덮는 시간이 4598초 중 1915초(41.6%)뿐이다.

전역 유사도는 0.74라 `global_sim_floor = 0.4` 폴백에 걸리지 않았다. 전역 지표가
국소 붕괴를 못 본다. **국소 방어선이 없다.**

`scripts/verify_timing.py`(= `make verify STEM=<회차>`)가 이 표를 기계적으로 다시
만든다. API를 부르지 않고 녹화 픽스처와 전처리 캐시만 읽는다. 다음에 같은 신고가
오면 귀로 듣지 말고 이걸 돌린다.

## D14 — UI는 매번 새로 전사하고, SRT 말고는 아무것도 남기지 않는다

D13의 사고는 두 층이었다. whisper가 무너진 것이 하나고, **무너진 기록을 다음
실행이 조용히 재사용한 것**이 둘이다. 예전 UI는 이렇게 돌았다:

1. `has_fixture(stem)` 이 참이면 → "기록된 응답 재사용"
2. 거짓이면 → `record_fixtures()` 로 녹화 후 그걸 다시 읽어 오프라인 실행

파일 이름(`stem`)이 키였다. 같은 이름의 다른 영상을 넣어도 옛 응답을 썼고,
반쪽만 녹화된 상태도 있었다. 사람은 자기가 방금 넣은 영상의 자막을 본다고
믿는데 실제로는 지난주 응답을 보고 있을 수 있었다.

이제 UI 경로에서 픽스처를 아예 쓰지 않는다.

- `pipeline.run(..., online=True, artifacts=False, workdir=<임시폴더>)` 한 번으로 끝난다
- `artifacts=False` → `trace.json`·리포트·검토용 SRT·`output.srt` 별칭을 쓰지 않는다
- `reuse_cache=False` → 지문 폴더를 만들지 않고 오디오를 매번 새로 뽑는다
- 임시 폴더는 `TemporaryDirectory`라 끝나면 오디오·조각까지 함께 사라진다
- 남는 파일은 원본 영상 옆의 SRT 하나

`vlogsrt record` 는 그대로 둔다. 그건 **테스트 픽스처를 만드는 개발용 명령**이고,
`make verify`와 픽스처 우선 개발 규율이 거기 걸려 있다. 앱 경로와는 분리됐다.

키가 없으면 오디오를 뽑기 **전에** 멈춘다. 몇 분 기다린 뒤 인증 오류를 보는 것은
낭비다. 그리고 `openai`의 예외는 `RuntimeError`가 아니라서 예전에는 화면에
트레이스백이 그대로 튀었다 — 이제 `Exception`을 받아 한 줄로 보여준다.

### 청크 길이 상한

`chunk_max_seconds = 600.0` 을 새로 뒀다. 예전에는 업로드 한도(24MB)만 봤고,
64kbps 모노에서 24MB는 **약 50분**이다. 그래서 77분 영상이 38분짜리 두 조각이
됐고 whisper-1이 조각 후반부에서 반복 루프에 빠졌다. 이제 크기와 길이 중
**더 잘게 나누는 쪽**을 따른다(`preprocess.chunk_count`). 77분이면 8조각이다.

## D15 — whisper 힌트는 화면에서 매번 정한다

D13의 방아쇠는 `vlogsrt.toml`에 박아둔 한 줄이었다.

```toml
prompt = "브이로그 내레이션입니다. 구어체 한국어이며 상호명과 지명이 자주 나옵니다."
```

설정 파일에 있으니 아무도 다시 보지 않았고, 영상마다 맞지도 않았다. 이제 비워두고
실행할 때마다 화면에서 받는다. 무엇을 넣고 돌렸는지는 로그에 `힌트   …`로 남는다.

`prompt`가 위험한 이유를 화면 안내에 적었다. whisper는 이 값을 **지시가 아니라
직전 자막 텍스트로** 보고 이어 쓴다. 그래서 지시문을 넣으면 그 문장이 자막이 된다.
넣을 것은 나올 법한 **단어**다.

### 국소 방어선

전역 유사도(`global_sim_floor`)는 0.74였고 폴백에 걸리지 않았다. 전역 지표가
국소 붕괴를 못 본다는 게 D13의 교훈이었다. 그래서 골격을 만든 직후에
`pipeline.warn_about_loops()`가 반복 구간을 세어 알린다. 판정은 바꾸지 않는다 —
`spine[]`은 그대로 두고 보고만 한다(불변 규칙 1). 실측 픽스처에서는 이렇게 나온다:

```
경고 whisper가 같은 문장을 되풀이한 구간 10개 · 1134초 (영상의 24.7%)
경고   12~582초 · 103회 · '구어체 한국어에서 한국어 자막을 사용합니다.'
경고   영상 시작부터 반복한다면 whisper 힌트(prompt)를 의심하라.
```

길이 0인 세그먼트 경고도 한 줄씩 찍던 것을 한 번의 요약으로 바꿨다. 452줄이
쏟아지면 정작 봐야 할 경고가 묻힌다.

## D16 — whisper에는 prompt를 보내지 않는다

D15에서 힌트 칸을 만들었다. 사람이 `"프랑스 여행 브이로그"`라고 적었다.
지극히 자연스러운 입력이다. 결과:

```
힌트   프랑스 여행 브이로그
경고   whisper가 같은 문장을 되풀이한 구간 9개 · 675초 (영상의 14.7%)
경고     12~576초 · 138회 · '한국 여행 브이로그'
```

12초부터 576초까지, 즉 **0:12~9:36 전체**가 날아갔다. 최종 SRT의 첫 큐가
09:42에서 시작한 이유다. D15에서 넣은 경고가 원인을 정확히 지목했다는 점은
다행이지만, 경고로 막을 일이 아니었다.

핵심은 이것이다. **whisper 텍스트는 최종 SRT에 한 글자도 들어가지 않는다**
(불변 규칙 2). whisper에서 얻는 것은 골격 시각뿐이다. 그런데 `prompt`는
whisper에게 지시가 아니라 직전 자막 텍스트로 들어가서, 알아듣기 힘든 구간을
만나면 그 문장을 이어 쓴다. **얻는 것이 없고 잃는 것은 골격 전체다.**

두 번의 실측이 같은 말을 한다:

| prompt | 반복 문장 | 횟수 | 길이 |
|---|---|---|---|
| `"브이로그 내레이션입니다…"` | `'구어체 한국어에서 한국어 자막을 사용합니다.'` | 103회 | 570초 |
| `"프랑스 여행 브이로그"` | `'한국 여행 브이로그'` | 138회 | 564초 |

그래서 `LiveTranscriber.whisper()`는 `prompt`를 넘기지 않는다. 사람이 준 힌트는
`gpt()`로 간다 — 최종 SRT의 글자를 만드는 모델이라 힌트가 실제로 쓸모 있는 곳이다.
`prompt`가 거부되면(400) 부가 인자만 떼고 한 번 더 부른다. 그 시점엔 whisper
응답을 이미 받아둔 상태라, 여기서 죽으면 약 $0.46이 통째로 버려진다.

### 넘침 가드

whisper가 한 구간을 통째로 놓치면 그 구간 정본 텍스트는 얹을 시각이 없다.
`map_cuts`가 남은 글자를 다음 절단점까지 몰아주므로 1초짜리 큐에 900자가 들어간다.
읽을 수 없는 자막이 되는 것으로 끝나지 않고 **멀쩡하던 이웃 큐까지** 밀려서
못 쓰게 된다 — 9분 공백이 4분치 정상 자막을 잡아먹었다.

`vlogsrt/overflow.py`가 큐 하나가 담을 수 있는 글자 수를 조판 한도와 읽기 속도
중 큰 쪽의 `overflow_factor`배로 제한한다. 넘치면 어절 경계에서 자르고 **얼마나
버렸는지 반드시 알린다.** 같은 픽스처로 재확인:

```
이전   큐 1019개  최대 881자  200자 넘는 큐 3개
지금   큐 1019개  최대  96자  200자 넘는 큐 0개
경고   정렬이 무너진 큐 5개에서 정본 1730자를 버렸다.
```

### 저역 제거를 정규화 앞에

문제의 앞 9분은 200Hz 아래 웅웅거림이 에너지의 절반이었다. 그 상태로 loudnorm을
걸면 **잡음에 맞춰 이득이 정해져 말소리가 오히려 눌린다.** 사람 목소리 기본
주파수는 남성도 85Hz 위라 120Hz 아래에는 말소리 정보가 없다.

| | 음성대역(300~3400Hz) | 저역(<200Hz) | 음절변조 |
|---|---|---|---|
| 앞 300초 · loudnorm만 | 30.4% | 51.4% | 0.398 |
| 앞 300초 · highpass 후 | **58.6%** | 26.8% | 0.384 |
| 앞 480초 · loudnorm만 | 43.0% | 36.2% | 0.229 |
| 앞 480초 · highpass 후 | **61.9%** | 23.1% | **0.340** |
| 뒤 3000초 · loudnorm만 | 72.0% | 7.0% | 0.360 |
| 뒤 3000초 · highpass 후 | **86.1%** | 2.7% | 0.360 |

잘 들리던 뒤 구간도 나빠지지 않는다. 마커 오디오로 타임라인 보존도 확인했다
(300초에서 오차 0.02초).

### 무음 처리는 원인이 아니었다

신고는 "무음 구간 없애는 부분에 문제가 있는 것 같다"였다. 아니다.

- `extract_audio`도 `make_chunks`도 오디오를 **한 샘플도 버리지 않는다.**
  청크 계획은 `[0, cut1], [cut1, cut2], …, [cutN, duration]`으로 전 구간을 덮는다
- 무음은 두 곳에만 쓰인다: 청크 절단점 고르기, `silent` 판정
- 실측에서 `silent` 판정을 받은 세그먼트는 **0개**였다 (ok 1231 / compression_fail 248)
- 앞 구간에 말소리가 있다는 것도 확인했다. 음절변조 0.26~0.33으로,
  뒤 구간(0.40)보다 약할 뿐 무음이 아니다

## D17 — 놓친 구간의 글자는 버리지 않고 그 시간대로 되돌린다

D16에서 넘침 가드를 넣었는데 **잘못된 쪽을 버렸다.** 큐가 받은 텍스트의 앞부분을
남기고 뒷부분을 버렸다. 절단점 사상의 정의상 큐가 받는 텍스트는
`[앞 큐가 끝난 시각, 이 큐가 끝난 시각]` 동안 나온 말이다. 즉 **앞부분은 앞 공백에서
나온 말이고, 큐가 실제로 덮는 시간에 나온 말은 뒤쪽이다.** 정확히 거꾸로 했다.

그리고 버릴 일이 아니었다. 그 시간대에 사람이 한 말이고, 놓인 자리만 틀렸다.

`vlogsrt/gapfill.py`가 `mapping.rescue_orphans`를 대체한다. 차이는 하나다.
rescue_orphans는 **전체 골격을 다시 정렬**해서 고아 구간의 텍스트를 찾았는데,
환청 구간에서는 그 정렬 자체가 무너진다(같은 문장이 100번 반복되니 대응점이
아무데나 붙는다). gapfill은 정렬을 믿지 않는다. **시간축만 본다.**

- 큐 앞의 빈 시간에 걸러낸 세그먼트가 있으면 그것을 시각의 닻으로 쓴다.
  환청 구간이라도 **세그먼트 경계는 오디오를 따라간다.** 못 믿을 건 텍스트뿐이고,
  그 텍스트는 어차피 최종 SRT에 안 들어간다(불변 규칙 2)
- 닻이 없고 큐가 넘치기까지 하면 그때만 균등 분할한다
- `silent` 판정은 닻으로 쓰지 않는다. "그 시간에 발화가 없었다"는 판정이라
  거기로 글자를 옮기면 없는 말을 만들어내는 셈이다
- 텍스트는 시간에 비례해 나눈다. 큐는 **꼬리**를 갖는다
- 붙어 있는 큐(간격 < `min_duration`)는 한 묶음으로 배분한다. 따로 하면 뒤엣것이
  자리를 못 얻는다 — 실측에서 933자짜리 큐 하나가 그렇게 살아남았다

골격에서 온 큐의 start/end는 건드리지 않는다(불변 규칙 3). 새로 만든 큐만
`time_estimated`를 달고 나가고 신뢰도는 `orphan_conf_max`로 눌러 둔다.

같은 픽스처(프롬프트 오염된 최악의 입력)로 잰 결과:

| | 이전 (버리기) | 지금 (되돌리기) |
|---|---|---|
| 최대 큐 글자수 | 881자 | **96자** |
| 200자 넘는 큐 | 3개 | **0개** |
| 정본에서 빠진 어절 | 2개 | **0개** |
| 덮은 시간 | 41.6% | 45.8% |
| 0~600초 큐 | 4개 | **67개** |
| 3분대(150~250초) 큐 | 0개 | **8개** |
| 최대 공백 | 569초 | 348초 |

남은 공백은 whisper가 세그먼트조차 주지 않았거나 0.85초 미만짜리만 준 구간이다.
거기까지 채우려면 시각을 순전히 지어내야 해서, 하지 않는다.

## D18 — 되풀이 구간은 판정 단계에서 강등한다 (2026-08-17)

### 증상

새 녹화(프롬프트 없음, 저역 필터 적용)에서도 앞 3분·뒤 6분 자막이 통째로 비었다.
로그: `'오 오 오 …' 30~177초 · 5회`, `'음..' 4247~4598초 · 210회`,
`빈 큐 538개를 버렸다`.

### 원인 사슬

세그먼트를 가로지르는 되풀이는 압축률(세그먼트 안쪽만 봄)을 통과해 **verdict가
ok로 남는다.** ok라서 (1) 큐가 되어 시간축을 차지하고 (2) 정렬 기준 문자열에
들어가 절단점을 무너뜨린다. 결과: 되풀이 구간 큐들이 빈 텍스트를 받고, gapfill
시점엔 그 빈 큐들 때문에 공백이 없는 것처럼 보이고, 마지막 refine에서 빈 큐가
버려지며 그 시간대가 통째로 사라진다.

### 결정

1. **`loops.demote`** — 골격 생성(fetch_spine)의 마지막에, 되풀이 구간의 ok
   세그먼트를 `compression_fail`로 강등한다. 큐도 정렬 재료도 아니게 되고
   gapfill의 시각 닻으로만 남는다. `silent`는 건드리지 않는다(발화 없음 판정을
   닻으로 바꾸면 없는 말을 만든다). 생성이 끝난 골격은 여전히 불변이다(규칙 1).
2. **빈 큐는 gapfill이 지운다** — 글자가 없으니 잃는 것도 없는데 자리만 차지해
   그 시간대를 공백이 아닌 것처럼 보이게 하기 때문이다.
3. **창 조각내기(`_burst`)** — 닻 창이 길거나 글자가 넘치면 `max_duration` /
   `max_chars_per_cue` 기준으로 나눈다. 조각은 `min_duration`보다 짧아지지 않는다.
   (실측: 8초 창에 359자가 큐 1개로 얹혔다.)
4. **앞으로 흘리기(`_spill_forward`)** — 큐가 용량을 넘치면 꼬리를 **뒤따르는**
   걸러낸 세그먼트 시간대로 보낸다(D16의 "첫 큐 0.77초에 900자"가 이 모양이다).
   마지막 묶음은 넘치지 않아도 보낸다 — 절단점 사상이 남은 정본 전부를 마지막
   큐에 얹기 때문이다. 기존의 "마지막 큐 전용" 뒤 공백 처리를 일반화한 것이다.

### 실측 (프롬프트 오염 픽스처, D17 대비)

| | D17 | D18 |
|---|---|---|
| 빈 큐 | 538개 상당 | **2개** |
| 뒤 되풀이 구간(3941~4510초) | 큐 1~2개 | **큐 58개 · 1229자** |
| 4200초 이후 큐 | 거의 없음 | **51개** |
| 최대 큐 글자수 | 96자 | 122자 |

### 남은 한계

이 픽스처의 178~582초는 여전히 비어 있다. 프롬프트 오염이 582초 **이후**의
whisper 텍스트까지 망가뜨려(길이 0 세그먼트 37%) 정렬이 앞 구간 정본을 582초
이후 큐들에 얇게 발랐고, 어느 큐도 용량(× `overflow_factor`)을 안 넘겨 흘림이
발동하지 않는다. 새 녹화는 whisper에 프롬프트가 안 가므로 이 이중 붕괴가
재현되지 않아야 한다. 재현되면 그때 `overflow_factor`를 근거와 함께 재검토한다.

## D19 — 2모델 사상을 버리고 whisper 단독 + gpt 검증으로 전환한다

날짜: 2026-08-17

### 증상

사상(mapping) 계열의 실패가 반복됐다. 0.77초 큐에 900자(D16), 9분 큐 점프,
그리고 D17·D18의 보상 로직 연쇄 — 최근 커밋 5개가 전부 gpt 텍스트를 whisper
시각에 꿰매는 봉합의 땜질이었다. 사용자 체감은 "영상과 자막 싱크가 안 맞는다".

### 근거

- D13 계측이 전처리를 이미 무죄 방면했다: 청크 오프셋 오차 0.0초, 필터
  타임라인 오차 0.000초. 병소는 전처리가 아니라 **두 텍스트를 정렬하는 사상
  단계 그 자체**다.
- 한 모델(whisper-1)이 시각과 텍스트를 동시에 내면 사상이 소멸하고, 싱크는
  구조적으로 보장된다. 텍스트 품질 하락은 gpt를 **검증자**로 돌려 플래그로
  보완한다 — 출력은 손대지 않는다.

### 결정 (사용자 지시)

1. **동기화가 1순위 목표다.** SRT의 시각·텍스트 전부 whisper-1 유래.
2. **gpt-transcribe는 검증 전용.** `verify.py`(신규)는 순수 함수 — 큐를 만들지도
   고치지도 못하고, 검증 on/off에 SRT는 바이트 동일. 검증 실패는 SRT를 막지 못한다.
3. **사상 계열 삭제**: `mapping.py`, `gapfill.py` + 테스트 41개.
   복귀 경로는 git — 마지막 사상 커밋은 `564d0be`.
4. `baseline` 서브커맨드 삭제 (`run --stop-after output`이 같은 역할).
   `redo`는 spine→cues→refine 재정제 전용.
5. 음질 필터 체인 제거는 P6에서 별도 커밋 (D20으로 기록).
6. `TRACE_VERSION` 인상 — 옛 trace는 `redo`에서 명시적 오류.

### 버리는 것

canonical(정본), 절단점 사상, 자모 정렬, 고아 복원, 신뢰도(conf), gapfill의
시각 추정. — 전부 "gpt 텍스트를 whisper 시각에 얹는다"는 전제 위의 구조물이고,
전제가 사라지면 존재 이유가 없다.

실행 단계는 `TASKS.md`의 P0~P8.

## D21 — 자막을 만드는 모델을 gpt-4o-transcribe-diarize 하나로 바꾸고, 검사 계층을 전부 걷어낸다

날짜: 2026-08-17

### 결정

1. 전사 모델은 **`gpt-4o-transcribe-diarize`** 하나다(`response_format=diarized_json`).
   whisper-1 경로를 삭제한다.
2. 파이프라인에서 **검사·재검증 계층을 전부 제거**한다 — 검증(`verify.py`),
   되풀이 강등(`loops.py`), 세그먼트 판정(verdict), 정제 결과 검사(`validate.py`),
   무음 검출과 무음 기준 청크 분할, 그리고 이들이 채우던 `report.md`.
3. 파이프라인이 하는 일은 이것뿐이다: 오디오 추출 → 한도 분할 → 전사 → 정제 → SRT.

### 근거

**whisper-1이 이 콘텐츠에서 실제로 무너졌다.** 77분 실행 로그(2026-08-17):

| 증상 | 실측 |
|---|---|
| 길이 0 세그먼트 | 청크 2에서 623개 중 414개 (66%) |
| 반복 환청 | 7구간 · 539초 = 영상의 11.7% (`'맥주'` 124회, `'칵테일'` 21회) |
| 검증 의심 큐 | 1377개 중 159개 (11.5%), 8청크 중 7청크 저유사도 |

강등이 환청을 걸러내면 그 11.7%는 자막 공백이 된다. 검증은 그 사실을 알려줄 뿐
고치지 못한다(설계상 출력 불변, D19의 4). 즉 **검사 계층은 whisper의 실패를
관측하는 장치였고, 모델을 바꾸면 관측 대상 자체가 사라진다.** 판정 지표
(`avg_logprob`, `compression_ratio`, `no_speech_prob`)는 whisper-1의
`verbose_json`에만 있어 새 모델에서는 계산조차 불가능하다.

### 왜 `gpt-transcribe`가 아니라 `-diarize`인가

`gpt-transcribe`(gpt-4o-transcribe)는 **타임스탬프를 반환하지 않는다.** 녹화된
픽스처가 증거다 — 38분 청크 하나가 `{"text": "…9067자…"}` 한 덩어리로 오고
`segments`가 없다. `timestamp_granularities`도 `verbose_json`도 이 모델에는
거절당한다. 시각이 없으면 SRT를 만들 수 없다.

세그먼트 시각을 주는 OpenAI 모델은 둘뿐이다: `whisper-1`(`verbose_json`)과
`gpt-4o-transcribe-diarize`(`diarized_json`). 후자를 택했다.

### 포기하는 것 (정직하게)

- **단어 타임스탬프.** diarize 응답에는 `words[]`가 없다. 긴 세그먼트를 자를 때
  쓰던 "가장 긴 휴지에서 자르기"가 불가능해져, 글자 수 비례 분할로 떨어진다.
  분할된 큐 안에서 최대 수백 ms의 오차가 생길 수 있다(큐 경계는 원본 세그먼트
  범위를 벗어나지 않는다).
- **무음 기준 청크 경계.** 균등 분할이라 경계가 말 중간에 떨어질 수 있고, 그
  경계에서 한두 어절이 사라질 수 있다. 대신 `chunk_max_seconds`를 600 → 1500으로
  올려 경계 수를 줄였다(600초는 whisper-1의 순차 디코딩 병리 때문이었고 — D13 —
  그 근거는 모델과 함께 사라졌다).
- **자동 품질 신호 전부.** 자막이 이상해도 프로그램은 아무 말도 하지 않는다.
  판단은 사람이 눈과 귀로 한다. 남은 자동 게이트는 `make verify`(오디오 포락선
  대조) 하나뿐이며 파이프라인 밖에 있다.

### 위험과 복귀

- **모델 가용성이 미검증이다.** 픽스처가 없어 오프라인에서 확인할 수 없었다.
  계정에 모델이 없으면 404가 나고 **과금은 되지 않는다.**
- 복귀 경로는 코드 수정이 아니라 설정 두 줄이다. `diarized_json`과
  `verbose_json`은 둘 다 `segments[].{start,end,text}`를 주므로 파서가 같다:

  ```toml
  [transcribe]
  transcribe_model = "whisper-1"
  transcribe_format = "verbose_json"
  ```

  단, 이렇게 되돌려도 판정·강등·검증은 돌아오지 않는다. 그것들이 필요하면
  이 커밋을 revert하라.
- 옛 `trace.json`은 읽히지 않는다(`TRACE_VERSION` 4.0).
- `tests/fixtures/api/`의 whisper·gpt 픽스처는 규칙대로 손대지 않았다. 새 경로가
  읽지 않으므로 고아로 남는다.

## D22 — `chunking_strategy`는 diarize 모델의 필수 인자다 (2026-08-17)

### 결정

`chunking_strategy`를 config로 올리고(기본 `"auto"`), **뺄 수 없는 인자**로 분류한다.
400 폴백은 "부가 인자를 전부 뗀다"에서 "오류가 지목한 인자만 뗀다"로 바꾼다.
첫 조각을 혼자 보내 인자 조합을 확정한 뒤 나머지를 병렬로 던진다.

### 근거

D21로 바꾼 모델을 처음 실제로 부른 결과(76.6분 영상), 전 조각이 즉시 거절당했다:

```
BadRequestError: Error code: 400 - {'error': {'message': 'chunking_strategy is
required for diarization models', 'type': 'invalid_request_error',
'param': 'chunking_strategy', 'code': 'invalid_value'}}
```

`gpt-4o-transcribe-diarize`는 30초를 넘는 입력에 `chunking_strategy`를 요구한다.
`"auto"`면 서버가 음성 활동 검출(VAD)로 자를 자리를 정한다 — **D21에서 우리가 지운
무음 검출을 서버가 대신하는 셈**이고, 그래서 되살릴 이유도 없다(규칙 4 유지).

400은 요청이 거절된 것이라 **과금되지 않았다.**

### 왜 폴백을 고쳤나

옛 폴백은 400이면 부가 인자를 **전부** 떼고 한 번 더 불렀다. 이번 실패에서 그
재시도는 무의미했다 — 빠진 것이 부가 인자가 아니라 필수 인자였으므로 두 번째
호출도 같은 400을 받았다. 두 가지를 고쳤다.

- **필수/부가 분리.** `model`·`response_format`·`chunking_strategy`는 폴백에서
  떨어지지 않는다. 이 셋이 거부당하면 고쳐야 할 **설정 키 이름**을 담아 멈춘다.
- **지목된 인자만 제거.** 오류 메시지가 `'prompt'`를 짚으면 `prompt`만 뗀다.
  아무 이름도 짚지 않을 때만 전부 뗀다. 힌트 하나 때문에 언어 지정까지 잃지 않는다.
- `temperature`를 부가 인자로 내렸다. 결정성 설정일 뿐이라 거부당해도 자막은 나온다.

### 왜 첫 조각을 먼저 보내나

옛 코드는 모든 조각을 동시에 던졌고, 인자가 틀리자 **조각 수만큼 똑같이 실패**했다.
첫 조각으로 인자를 확정하면 실패는 업로드 한 번으로 끝나고, 성공하면 남은 조각은
이미 정리된 인자로 한 번에 통과한다. 첫 조각의 전사 자체는 어차피 필요한 일이라
버려지는 시간이 아니다. 대가는 병렬도 하락(전체 ≈ 1조각 + 나머지 병렬)이다.

### 타이밍은 여전히 모델이 만든다

"타이밍을 룰베이스로 찾아도 된다"는 허락을 받았지만 쓰지 않았다. `chunking_strategy`
하나로 `segments[].{start,end,text}`가 정상적으로 돌아오므로 규칙 1을 어길 이유가
없다. 글자 수 비례로 시각을 지어내면 76분 영상에서 오차가 누적되고, **틀렸다는
사실이 겉으로 드러나지 않는다** — D13·D19·D21이 전부 그 조용한 오류의 기록이다.
규칙에 없는 시각이 필요해지면 코드가 아니라 이 문서에 먼저 온다.

### 복귀

whisper-1로 되돌릴 때는 세 줄이다. `chunking_strategy`를 비우지 않으면 whisper가
모르는 인자를 받아 400이 난다.

```toml
[transcribe]
transcribe_model = "whisper-1"
transcribe_format = "verbose_json"
chunking_strategy = ""
```

## D23 — 어떤 구간도 조용히 버리지 않는다 (2026-08-17)

### 결정

불변 규칙 9를 새로 세운다. **자막에 구멍을 낼 수 있는 모든 경로를 멈춤으로 바꾼다.**
경고가 아니라 `RuntimeError`다. 함께 `languages`를 단수형 `language`로 되돌린다.

### 근거 — `languages`

D22 수정 후 실제 호출이 통과했고, 첫 조각에서 부가 인자 하나가 걸러졌다:

```
WARN 전사 청크 0: API가 ['languages']를 거부했다(Error code: 400 - {'error':
{'message': "The 'languages' parameter is not supported for this model.",
'param': 'languages', 'code': 'invalid_parameter'}}). 빼고 다시 부른다.
```

폴백이 설계대로 동작해 전사는 살았지만, 매번 조각 하나를 버리는 400을 맞을 이유가
없다. `extra_languages`의 기본값을 비워 단수형 `language`가 나가게 했다.
`languages`가 거부당하면 단수형으로 **바꿔서** 다시 부르도록 폴백도 고쳤다 —
복수형이 막혔다고 언어 지정 자체를 잃으면 모델이 한국어를 자동 판별해야 한다.

### 근거 — 구간 손실

파이프라인에 자막을 조용히 비울 수 있는 구멍이 넷 있었다. 전부 막았다.

| 자리 | 옛 동작 | 지금 |
|---|---|---|
| `parse_segments` | `end <= start`면 **글자째로 버림** | 남긴다. `end = start`로 접고 정제가 늘린다 |
| `build_spine` | 빈 응답 청크를 조용히 통과 | 멈춘다. 조각 번호와 오프셋을 알려준다 |
| `refine.drop_empty` | 빈 큐를 버리고 경고 한 줄 | `reject_empty` — 멈춘다 |
| `make_chunks` | 만든 조각 길이를 안 봄 | `verify_coverage` — 계획보다 짧으면 멈춘다 |

가장 컸던 것은 첫 줄이다. 시각이 뒤집혔다는 이유로 **말 자체를 버리고 있었다.**
그 판단은 whisper-1 시절의 유산이다(길이 0 세그먼트가 66%까지 나왔다, D21).
지금 모델에는 그런 병리의 증거가 없고, 있더라도 글자를 버릴 이유는 되지 못한다 —
시각은 정제가 규칙 3의 한도 안에서 고칠 수 있지만 사라진 말은 되돌릴 수 없다.

### 규칙 4와의 관계

이건 **검사 계층의 부활이 아니다.** 자막의 품질을 판정하지 않고, 의심 표시도
경고도 리포트도 만들지 않는다. 세는 것은 오직 **입력이 다 들어갔는가**다.
결과는 통과 아니면 멈춤 두 가지뿐이라 사람이 읽고 판단할 플래그가 생기지 않는다.
품질 판단은 여전히 사람이 눈과 귀로 한다.

### 대가

빈 청크 하나가 실행 전체를 죽인다. 76분 영상이라면 그 조각의 원인을 확인하고
다시 돌려야 하고, 그건 비용이다. 그래도 **25분짜리 구멍이 뚫린 SRT가 조용히
나오는 것보다 낫다** — 뚫린 자막은 영상을 끝까지 보기 전까지 아무도 모른다.
D13·D19·D21이 전부 그 조용한 오류의 기록이다.

`chunk_duration_tolerance = 0.5`초는 외부 근거가 없는 값이다. mp3 인코더 패딩
(~26ms)은 조각을 늘리지 줄이지 않으므로 여유가 넉넉하다는 판단일 뿐이다.

## D24 — 시각은 오디오에서, 글자는 모델에서 (2026-08-17)

### 결정

모델을 `gpt-4o-transcribe`로 바꾸고, **자막 시각을 모델이 아니라 오디오에서 구한다.**

1. `ffmpeg silencedetect`로 무음을 찾아 **발화 구간**을 만든다. 이것이 시각의
   유일한 출처다.
2. 발화 구간을 40초 안팎의 **묶음**으로 모아 한 번에 전사한다. 자르는 자리는
   항상 무음 한가운데라 말이 잘리지 않는다.
3. 묶음이 돌려준 텍스트를 그 묶음의 발화 구간에 **길이 비례로 배분**한다.
4. `gpt-4o-transcribe-diarize` 경로는 삭제한다. 경로 하나, 진실 하나.

D21~D23(단일 diarize 모델)을 대체한다. 복귀는 설정이 아니라 `git revert`다.

### 근거

`gpt-transcribe`는 **타임스탬프를 주지 않는다.** 녹화된 픽스처가 증거다 —
`tests/fixtures/api/fr_day_1_2_fhd.gpt.json`의 응답 필드는
`['text', 'languages', 'logprobs', 'usage']`이고, 38분 청크 하나가 9,067자 한
덩어리로 온다. D21에서 이 사실 때문에 diarize를 골랐었다.

이번에는 반대로 간다. 시각을 모델에게 묻지 않고 **오디오에서 직접 잰다.**
그러면 모델 선택이 타이밍과 분리되고, 모델은 자기가 잘하는 일(받아쓰기)만 한다.

시각의 해상도는 **자르는 단위**가 정한다. 무음 기준 발화 구간은 보통 1~4초라,
배분 오차가 그 안으로 제한된다. 고정 길이 창(30초 균등 분할)이었다면 오차가
창 크기까지 벌어지고 경계가 말 중간에 떨어졌을 것이다.

### 배분 알고리즘

```
어절 단위로 쪼갠다 → 구간 길이 누적 비율로 누적 목표 글자 수를 정한다
→ 목표에 닿을 때까지 어절을 통째로 담는다 → 남으면 마지막 구간에 붙인다
```

누적 목표를 쓰는 이유: 구간마다 독립적으로 반올림하면 오차가 뒤로 쌓인다.
어절을 쪼개지 않는 이유: 단어가 두 자막에 걸치면 읽을 수 없다.
한국어는 음절 문자라 **글자 수 ∝ 발화 시간**이 대체로 성립한다.

### 규칙 4와 무음 검출

D21에서 무음 검출을 지웠다가 여기서 되살린다. 모순이 아니다.
- D21의 무음 검출은 **청크 경계를 예쁘게 자르는 보조 장치**였고, 실패하면
  "강제로 잘랐다" 경고가 로그를 덮었다.
- D24의 무음 검출은 **타이밍의 유일한 출처**다. 없으면 SRT를 만들 수 없다.

품질을 판정하지 않고 플래그도 리포트도 만들지 않는다는 점은 그대로다.

### 규칙 9 완화

D23에서 "구간 손실 = 멈춤"으로 세웠던 것을 **"구간 손실 = 경고 + 계속"**으로
바꾼다. 사용자 결정이다. 76분 실행이 빈 조각 하나로 통째로 죽는 대가가 크다.

원칙은 남는다: **어절은 절대 버리지 않고**(배분하고 남으면 마지막 구간에 붙인다),
조용히 사라지는 것도 없다(전부 로그에 남는다). 침묵만 금지고, 멈춤은 아니다.

### 포기하는 것 (정직하게)

- **모델이 아는 시각.** diarize는 자기가 어디서 무슨 말을 들었는지 알고 답했다.
  이제는 우리가 소리의 크기만 보고 나눈 구간에 글자를 끼워 넣는다. 모델이 말과
  다른 글자를 주면(추임새 생략, 배경 대화 받아쓰기) 글자가 엉뚱한 구간에 붙는다.
- **연속 문맥.** 40초 조각은 앞뒤를 모른다. 문장이 조각 경계에서 끊기면 받아쓰기
  품질이 떨어질 수 있다. 자르는 자리가 무음이라 최악은 피하지만 보장은 아니다.
- **무음이 안 잡히는 구간.** BGM이나 소음이 깔리면 발화 구간이 통짜가 되고,
  타이밍이 고정 창 방식으로 퇴화한다. 묶음당 구간 수를 로그에 찍어 눈에 보이게 한다.

### 근거 없는 값 넷

| 값 | 기본 | 성격 |
|---|---|---|
| `silence_threshold_db` | -35.0 | 옛 값 그대로. 소음 있는 회차는 올려야 한다 |
| `silence_min_duration` | 0.3 | 0.5면 발화 구간이 굵어져 배분 오차가 커진다 |
| `min_speech_duration` | 0.15 | 이보다 짧으면 말이 아니라 잡음으로 본다 |
| `batch_max_seconds` | 40.0 | 요청 수와 배분 오차의 절충 |

Netflix TTSG 근거값(`min_duration`, `min_gap`)과 달리 **회차별 조정 대상**이다.

## D25 — 시각을 whisper로 되돌리고, 분할은 자를 자리만 고른다 (2026-08-17)

### 결정

D24를 폐기한다.

1. **`silencedetect` → 무음 → 발화 구간 → 배분 경로를 전부 삭제한다**
   (`spans.py`, `align.py`).
2. **자르는 유일한 기준은 모델의 최대 입력(25MB, 안전 여유 24MB).** 그 한도로 나눈
   목표 경계 근처 ±5초에서 **가장 조용한 지점**을 찾아 자른다. 못 찾으면 목표 지점
   그대로 자른다.
3. **시각과 글자는 `whisper-1`(`verbose_json`)이 만든다.** `세그먼트 시각 + 조각
   오프셋`이 원본 오디오 시각 그대로이며, 그 밖의 계산은 없다.
4. **`gpt-4o-transcribe`는 옵션 검증(`--verify`).** 출력을 절대 바꾸지 않는다.

### 근거 — D24가 무엇을 깨뜨렸나

실제 실행에서 세 가지가 동시에 무너졌다.

**① 초반·마지막 3~6분이 통째로 날아갔다.** `speech_spans`는 `cursor = 0.0`에서
시작해 무음의 여집합만 발화 구간으로 삼는다. `silencedetect`가 "0~200초는 무음"이라
판정하면 그 구간은 발화 구간에 **아예 들어가지 않는다.** 끝도 같다 — 마지막 무음이
영상 끝까지 이어지면 그 뒤로 자막이 없다. 조용한 인트로/아웃트로가 버려진 것이다.

**② 타이밍이 어긋났다.** 무음이 드물게 잡히면 발화 구간이 60초짜리가 되고, 그 60초에
글자가 균등하게 퍼진다. 중간 침묵만큼 자막이 통째로 밀린다. 시뮬레이션: 무음이 60초에
한 번만 잡히면 발화 구간 77개가 전부 60초짜리다.

**③ 무음이 0개면 요청이 거절된다.** BGM·소음이 깔리면 발화 구간이 통짜 1개가 되고,
`group_spans`의 "첫 구간은 한도를 넘겨서라도 받는다"가 크기 한도를 무력화한다.
77분이면 37MB 파일 하나를 24MB 한도 너머로 업로드 → 400.

셋 다 뿌리가 같다. **무음 검출이 "어느 구간이 말인가"를 정했고, 그 판단이 틀리면
구간이 사라진다.** `silence_threshold_db` 하나에 자막 전체가 걸려 있었다.

### 진폭 0 탐색이 무음 검출과 다른 점

되살린 것처럼 보이지만 하는 일이 다르다.

| | D24 무음 검출 | D25 진폭 0 탐색 |
|---|---|---|
| 정하는 것 | 어느 구간이 **말인가** | **어디서 자를까** |
| 커버리지 | 무음 판정 구간은 사라진다 | 조각이 `[0, duration]`을 빈틈없이 덮는다 |
| 틀리면 | 자막이 통째로 없어진다 | 경계가 말 중간에 떨어질 뿐 |
| 못 찾으면 | 통짜 1구간 → 400 | 목표 지점에서 그냥 자른다 |

**구간이 사라질 수 있는 코드 경로 자체가 없다.** 이걸 규칙 4로 못 박았다:
"분할은 자를 자리만 고른다. 구간을 고르지 마라."

### 오프셋을 ffmpeg에게 묻는 이유

세그먼트 분할은 `-f segment -segment_times … -c copy` 한 번으로 끝내고, 각 조각의
시작 시각은 `-segment_list`가 내놓는 CSV의 **실제 값**을 쓴다. mp3는 프레임
경계(~26ms)에서 잘려 요청한 시각과 미세하게 다르다. 요청값을 오프셋으로 쓰면 그
차이가 자막 전체에 실린다(D13이 그 사고였다). 재인코딩도 없다.

### 실측된 위험 — 38분 조각

모델 한도를 유일한 기준으로 삼으면 77분 영상이 **38.5분짜리 조각 2개**가 된다.
그건 D13·D21에서 실제로 무너진 설정이다:

| 증상 | 실측 |
|---|---|
| 길이 0 세그먼트 | 청크 2에서 623개 중 414개 (66%) |
| 반복 환청 | 7구간 · 539초 = 영상의 11.7% |

`chunk_max_seconds = 600`이 있었던 이유가 이것이었다. 사용자 지시대로 모델 한도를
기준으로 삼되 **탈출구를 남긴다**: `vlogsrt.toml`에서 `chunk_max_bytes`를 낮추면
조각이 그만큼 늘어난다. 예: `4_800_000`(≈10분) → 77분이 8조각. 코드 수정이 아니라
한 줄이다. `--verify`가 정확히 이 증상(청크 유사도 급락)을 잡는 장치다.

반복 환청이 나와도 **빼지 않는다**(규칙 9). 자막에 쓰레기가 보이는 편이 539초짜리
공백보다 낫다 — 공백은 초반·마지막이 날아간 것과 같은 부류의 손실이다.

### 검증을 다시 넣는 이유와, 넣지 않는 것

D21에서 검증 계층을 지웠던 근거는 "whisper의 실패를 관측하는 장치였는데 모델이
바뀌어 관측 대상이 사라졌다"였다. whisper가 돌아왔으므로 그 근거도 함께 돌아온다.

다만 **표시만 한다.** `verify.py`는 큐를 만들지도 고치지도 지우지도 못하고
`refine`·`output`을 import하지 않는다. 검증 on/off에 SRT 바이트가 동일하다는 것을
불변 테스트가 강제한다. `loops.demote`(되풀이 강등), `validate`, `mapping`,
`gapfill`은 되살리지 않는다 — 전부 구간을 없애는 부류다.

### 힌트가 검증 모델로만 가는 이유

whisper는 `prompt`를 지시가 아니라 **직전 자막 텍스트**로 읽는다. 실측 두 번 모두
그렇게 무너졌다 — `"프랑스 여행 브이로그"` 한 줄이 `'한국 여행 브이로그'` 138회·564초를
낳았다(D13, D16). 힌트와 `keywords`는 `gpt-4o-transcribe` 쪽에만 실린다.
`check_invariants.py`가 whisper 호출 인자를 기계적으로 검사한다.

### 포기하는 것

- **고유명사 교정이 자막에 직접 반영되지 않는다.** 힌트는 검증 모델만 보므로,
  틀린 고유명사는 검증이 **짚어줄 뿐** 고치지 못한다. 고치려면 사람이 SRT를 손본다.
- **긴 조각의 품질.** 위 위험표대로다.
- `TRACE_VERSION` 6.0 — 옛 `trace.json`은 읽히지 않는다.

### 덧붙임 — 검증 모델과 기본값 (같은 날)

- **모델 이름은 `gpt-transcribe`다.** `gpt-4o-transcribe`가 아니다 — 이 프로젝트가
  D19 시절부터 쓰던 이름이고 `tests/fixtures/api/*.gpt.json`이 그 모델로 녹화됐다.
- **검증은 기본으로 켜 둔다.** 옵션으로 두려다 바꿨다. 근거: 검증은 **출력을 바꿀 수
  없으므로**(규칙 5, 불변 테스트가 바이트 동일성을 강제한다) 켜서 손해 볼 것이 자막에는
  없다. 대가는 비용 2배뿐이고, 그건 `--no-verify` 한 번으로 되돌린다.
  whisper의 반복 환청은 실측된 병리인데(D13: 539초, 11.7%) 그걸 잡는 유일한 장치를
  기본으로 꺼두면 사람이 켜는 걸 잊는다.
- 힌트가 살아남았다. 검증 모델이 있으니 보낼 곳이 생겼다 — 다만 **고유명사를 직접
  고쳐주지는 않는다.** 검증이 짚어줄 뿐 고치는 건 사람이다.

## D26 — 조각을 10분으로 낮춘다. 모델 한도는 너무 컸다 (2026-08-18)

### 결정

`vlogsrt.toml`의 `chunk_max_bytes`를 `4_800_000`(64kbps에서 정확히 600초)으로 낮춘다.
코드 기본값(24MB = 모델 한도)은 그대로 둔다 — 한도는 여전히 한도고, 프로젝트가 그보다
보수적인 값을 고른 것이다.

### 근거 — D25가 예고한 위험이 실현됐다

76.7분 영상을 모델 한도(24MB ≈ 38분 × 2조각)로 돌린 결과를 SRT에서 직접 셌다:

| | 되풀이 구간 | 시간 |
|---|---|---|
| 조각 0 (0~38.2분) | 22 | 157초 |
| **조각 1 (38.2~76.6분)** | **10** | **1746초** |
| 합계 | 32 | 1903초 = **영상의 41.4%** |

가장 긴 것: `49:01~76:39` 한 문장이 **1668회, 1658초**. **마지막 27분이 통째로 한
문장의 반복이다.** 38분 조각의 중간에서 whisper가 무너진 뒤 끝까지 회복하지 못했다.

D21의 실측(539초, 11.7%)보다 나빴다. `chunk_max_seconds = 600`이 있던 이유가
이것이었고(D13), 그 값을 바이트로 옮긴 것이 `4_800_000`이다.

### 검증은 결백하다

사용자가 "검증 때문인가" 물었다. 아니다. 그리고 그 질문이 나오지 않도록 구조가 이미
잡혀 있다:

- SRT는 검증이 시작되기 **전에** 저장된다
- `verify.py`는 `refine`·`output`·`layout`을 import하지 못한다(`check_invariants.py`)
- 불변 테스트가 **검증 on/off SRT 바이트 동일**을 강제한다

오히려 검증이 이 사고를 `되풀이 10구간 1746초`로 잡아 알려줬다. **검증을 기본으로
켜 둔 판단(D25 덧붙임)이 여기서 값을 했다.**

### 대가

조각이 2개에서 8개로 늘었다. 요청 수가 늘지만 비용은 분당 과금이라 그대로다
(자막 $0.46 + 교차 확인 $0.46). 조각 경계가 7개로 늘어 그 자리에서 어절을 잃을
확률이 커지는데, 경계를 ±5초 안에서 가장 조용한 지점으로 옮기므로 말 중간에
떨어지지는 않는다.

### 남은 위험

10분 조각에서도 whisper가 무너질 수 있다. 그때는 되풀이가 최대 10분으로 제한되고,
검증이 그 구간을 짚어준다. 더 낮춰야 하면 같은 한 줄이다.

## D27 — 되풀이는 다시 물어서 고친다. 규칙 4·5·9를 그만큼 연다 (2026-08-18)

### 결정

되풀이 구간을 **그 구간만 다시 잘라 여러 모델에게 다시 묻고, 회복되면 갈아끼운다.**
회복하지 못하면 첫 장만 남기고 그 구간을 비운다. 새 계층 둘이 생긴다:

| 모듈 | 하는 일 | 순수한가 |
|---|---|---|
| `repetition.py` | 되풀이 검출. **자리만 짚는다** | 순수 |
| `repair.py` | 다시 묻고 판정하고 갈아끼운다 | API 호출(전사 경계 경유) |

같은 날 세 가지를 더 고쳤다. 셋 다 **되풀이가 애초에 덜 생기게 하는** 쪽이다:

1. 조각 한도가 **바이트와 초 둘 중 작은 쪽**이 된다 (`chunk_max_seconds = 600`)
2. `vlogsrt.toml`을 **패키지 기준으로도 찾는다**
3. whisper의 신뢰도 메타(`compression_ratio`·`avg_logprob`·`no_speech_prob`)를
   `Segment`에 **남긴다**

### 근거 1 — D26의 한 줄이 실행에 닿지 않았다

D26이 `chunk_max_bytes`를 4.8MB(≈10분)로 낮춘 뒤에 받은 실행 로그다:

```
조각 2개
조각 0 (0~2294초)   유사도 0.74
조각 1 (2294~4598초) 유사도 0.09
2941~4609초 되풀이 1668회: '꼬불꼬불 꼬불하고 여기 안으로 들어갔다가'
```

**38분 조각 2개다.** 설정이 적용되지 않았다. `config.PROJECT_TOML`이
`Path("vlogsrt.toml")` — 현재 디렉터리 상대 경로였고, 다른 폴더에서 실행하면(UI가
그렇다) 파일을 못 찾고 코드 기본값 24MB로 돌아갔다. 프리셋은 이미 패키지 기준
폴백이 있었는데 프로젝트 설정만 없었다.

고친 것이 셋이다: 설정 파일을 패키지 기준으로도 찾고, **조각 길이를 로그에 반드시
찍고**(`조각 8개 · 가장 긴 조각 9.6분`), 초 한도를 코드에 되살렸다. 세 번째가
핵심이다 — 바이트는 길이의 대리 변수일 뿐이라, 비트레이트가 바뀌면 같은 24MB가 다시
38분이 된다. **대리 변수로 막던 것을 직접 막는다.**

### 근거 2 — whisper의 자동 방어는 이 병리에 원리적으로 반응하지 않는다

`tests/fixtures/api/fr_day_1_2_fhd.whisper.json`의 세그먼트 1479개를 직접 셌다:

| | 값 |
|---|---|
| `compression_ratio > 2.4` (whisper 레퍼런스의 되풀이 임계값) | **248개** |
| 그중 `avg_logprob < -1.0` | **0개** |
| 그 248개의 `avg_logprob` 범위 | −0.38 ~ −0.09 |
| 그 248개의 `temperature` | 전부 `0.0` |

OpenAI 전사 API의 자동 온도 상승은 **로그 확률**을 보고 발동한다. 그런데 되풀이는
**모델이 확신하면서 무너지는** 병리다 — 로그 확률이 오히려 좋다. 그래서 폴백이 한 번도
걸리지 않았고, `temperature`는 끝까지 0.0이었다.

**되풀이를 잡는 신호는 응답에 이미 들어 있었다.** `compression_ratio`가 그것이고,
우리는 `parse_segments`에서 그 필드를 읽지도 않고 버리고 있었다. 이제 남긴다.
분포도 깨끗하게 갈렸다 — 2.4와 3.0 사이에 세그먼트가 **하나도 없다.**

### 근거 3 — 조각을 아무리 줄여도 되풀이 자체는 남는다

10분 조각에서도 whisper는 무너질 수 있다. D26이 "남은 위험"으로 적어둔 그대로다.
조각 크기는 **피해 범위**를 줄일 뿐 병리를 없애지 못한다. 없애려면 무너진 구간을
다시 물어보는 수밖에 없다.

### 무엇이 바뀌고 무엇이 안 바뀌나

바뀌지 않는 것부터. **시각은 여전히 whisper `segments[]`에서만 온다**(규칙 1).
재전사도 whisper 호출이고, 조각 오프셋도 ffmpeg가 CSV로 알려준 실제값이다. 재전사
조각은 1차 분할과 **같은 장치**(`split_at`)로 자른다. 바뀌는 것은 **어느 응답이 그
구간을 덮느냐** 하나뿐이다.

`verify.py`도 그대로다. 검증은 여전히 표시만 하고, 검증 on/off SRT 바이트 동일성을
불변 테스트가 강제한다. **재전사는 검증이 아니다** — 자리부터 다르다:

```
1차 전사 → [되풀이 검출 → 재전사 → 골격 조립] → 정제 → SRT 저장 → 검증
                    ↑ 여기서 끝난다                              ↑ 여기는 못 건드린다
```

골격은 재전사가 끝난 **뒤에** 조립되고, 그때부터 불변이다(규칙 2). 그래서 규칙 2도
깨지지 않는다 — 조립된 골격을 고치는 코드는 없다.

### 규칙 4를 어떻게 여는가

지금까지: **"분할은 자를 자리만 고른다. 구간을 고르지 마라."**
앞으로: **"구간을 빼려고 고르지 마라. 다시 묻기 위해 고르는 것은 허용한다."**

D24가 무너진 이유는 구간을 고른 것 자체가 아니라 **고른 구간을 커버리지에서 뺐기**
때문이다. 무음이라고 판정한 구간은 자막에 아예 안 들어갔고, 그렇게 초반·마지막
3~6분이 날아갔다. 재전사는 정반대다 — 고른 구간을 **같은 길이로 다시 덮는다.**
회복하든 못 하든 그 구간의 시간 범위는 그대로 남는다.

`check_invariants.py`가 그 선을 기계로 지킨다: `repair.py`는
`refine`·`output`·`layout`·`verify`를 import하지 못하고, 반대로 조판 계층은
`repair`·`repetition`을 import하지 못한다. 판정이 파이프라인 아래로 새지 않는다.

### 규칙 9를 어떻게 여는가 — 여기가 진짜 대가다

지금까지 규칙 9는 절대적이었다: **"조용히 사라지는 구간은 없다."** D25·D26은
"자막에 쓰레기가 보이는 편이 539초짜리 공백보다 낫다"고 판단했다.

**그 판단을 되풀이에 한해 뒤집는다.** 근거는 실측된 규모다. 1668회·1658초는
"쓰레기가 좀 보이는" 수준이 아니라 **마지막 27분이 통째로 한 문장**인 상태다.
그건 정보가 아니라 소음이고, 보는 사람에게는 자막이 없느니만 못하다.

다만 **접기는 마지막 수단이다.** 여기 오기 전에:

1. 되풀이 구간을 다시 잘라 whisper에 **1차와 다른 온도로** 다시 묻는다
2. 심판 모델(`gpt-transcribe`)이 같은 구간을 듣고 "여기 되살릴 말이 있나" 답한다
3. 심판이 "있다"고 하면 온도를 올려 **한 번 더** 산다
4. 그래도 회복 못 하면 그때 첫 장만 남긴다

그리고 **조용히는 아니다.** 접힌 구간은 전부 `WARN`으로 뜨고, `trace.json`의
`repairs[]`에 무엇이 몇 장에서 몇 장이 됐는지 남는다.

### 심판 모델이 실제로 하는 일

`gpt-transcribe`는 글자만 주고 시각을 만들지 않는다. 그래서 **자막을 직접 고치지
못한다** — 규칙 1이 막는다. 대신 **whisper에 한 번 더 돈을 쓸 값어치가 있는지**를
정한다. 심판이 멀쩡한 말을 들었다면 그 구간에는 되살릴 발화가 있다는 뜻이고,
심판도 되풀이를 들었다면 화자가 정말 되풀이한 것이거나 회복 불가능한 오디오다.

두 모델의 표가 이렇게 갈린다:

| whisper 재호출 | 심판 | 결과 |
|---|---|---|
| 멀쩡 | 멀쩡 | 갈아끼운다 |
| 멀쩡 | 되풀이 | 갈아끼운다 (재전사가 더 나은 자막이다) |
| 되풀이 | 멀쩡 | 온도를 올려 한 번 더 → 그래도 안 되면 접는다 |
| 되풀이 | 되풀이 | 즉시 접는다 (더 살 이유가 없다) |

### 비용

되풀이 구간에만 붙는다. 멀쩡한 영상은 **추가 비용 0원**이다 — 되풀이가 없으면
`repair`는 API를 한 번도 부르지 않는다.

되풀이가 많으면 비싸진다. `fr_day_1_2_fhd` 픽스처(38분 조각 시절)로 재보면 재전사
대상이 5구간 1195초(영상의 26.0%)이고, 재전사 + 심판이 약 **$0.24**다. 자막 $0.46 +
교차 확인 $0.46에 얹히는 26%. 사용자 로그의 1920초라면 약 $0.38이다.

**다만 이 숫자는 조각이 38분이던 시절의 것이다.** 조각을 10분으로 강제하면 되풀이
자체가 줄고 비용도 그만큼 줄어든다. 재전사 비용이 크다는 것은 곧 앞단이 실패하고
있다는 신호이므로, 그 숫자를 로그로 보는 것 자체가 값을 한다.

### 압축률은 **창 안에서만** 재야 한다

구현 리뷰가 잡은 결함이고, 하마터면 이 결정 전체를 무의미하게 만들 뻔했다.

zlib 압축률은 **입력이 길어지기만 해도 올라간다.** 처음 구현은 재전사 결과 전체를
이어붙여 한 번에 쟀는데, 그러면 임계값 검사가 길이 검사가 된다. 실측:

| 이어붙인 정상 세그먼트 | 글자 | 압축률 | 판정 |
|---|---|---|---|
| 100개 | 990 | 2.12 | 정상 |
| 300개 | 2,970 | 2.31 | 정상 |
| **529개** | **5,225** | **2.45** | **되풀이 ✗** |
| 1000개 | 9,900 | 2.67 | 되풀이 ✗ |

whisper 스스로 `compression_ratio <= 2.4`라고 표시한 세그먼트만 모은 것이다. 즉
**27분짜리 구간을 완벽하게 되살려도 접혔다** — D27이 고치려던 바로 그 사고를 D27이
다시 일으키는 셈이었다. 심판 모델도 같은 자로 재고 있었으니 "한 번 더 시도" 탈출구도
같이 막혀 있었다.

whisper의 레퍼런스 구현이 이 임계값을 재는 곳도 **30초 디코딩 창 하나**다. 그래서
우리도 창으로 잰다(`loop_ratio_window_words = 60`, 반 창씩 겹쳐 훑는다). 창 크기는
실측으로 골랐다:

| 창(어절) | 정상 최대 | 정상 오판 | 되풀이 최소 | 되풀이 검출 |
|---|---|---|---|---|
| 20 | 1.76 | 0% | 1.42 | 91.9% |
| 40 | 2.00 | 0% | 2.10 | 97.6% |
| **60** | **2.01** | **0%** | **3.01** | **100%** |
| 120 | 2.15 | 0% | 5.48 | 100% |

60어절에서 정상(2.01)과 되풀이(3.01)가 임계값 2.4를 사이에 두고 갈린다.

세그먼트가 있을 때는 더 정확한 자가 있다. 재전사 응답은 `verbose_json`이라 세그먼트
경계와 whisper 자신의 지표를 함께 주므로, **되풀이가 덮는 시간의 비율**로 판정한다
(`repetitive_share`). 일부만 되풀이인 결과를 통째로 버리지 않는다 — 원본보다는 낫다.

### 구간은 세그먼트에서 나온다. 그 반대가 아니다

두 번째로 잡힌 결함. 처음 구현은 `되풀이 ± 여유`로 구간을 정하고 **그 구간에서
시작하는** 세그먼트를 걷어냈다. 여유가 세그먼트 한복판에 떨어지면 이렇게 된다:

```
되풀이 10~18초 · 여유 2초 → 구간 8~20초
세그먼트 19.0~26.0초 "뒤로 걸쳐 나가는 문장"  ← 19초에서 시작하니 걷어낸다
재전사 조각은 20초에서 끝난다                  ← 20~26초는 다시 묻지도 않았다
```

**6초가 경고 없이 사라졌고, 판정은 `replaced`로 찍혔다.** 접기와 달리 이건 규칙 9가
허용한 예외가 아니다 — 되풀이도 아닌 구간이 조용히 없어진 것이다. 반대쪽 경계에서는
같은 오디오를 원본과 대체본이 함께 덮어 글자가 두 번 나왔다.

그래서 순서를 뒤집었다. **세그먼트를 통째로 데려간 뒤 그 범위를 구간으로 삼는다**
(`_assign` → `_Plan.owned` → `span`). 여유에 닿기만 해도 세그먼트 전체를 가져가므로,
구간 경계는 언제나 세그먼트 경계이고 걷어낸 것은 반드시 다시 물어본 것이다.
한 세그먼트는 한 계획에만 속하고, 그래도 구간이 겹치면(whisper가 시각이 겹치는
세그먼트를 내놓을 때) **그 계획을 버린다** — 못 고치는 것이 잘못 고치는 것보다 낫다.

### 실패는 손실로 번지지 않게 한다

리뷰가 같은 부류로 셋을 더 잡았다. 전부 "재전사가 제 일을 못 할 때 자막이 사라지는"
경로였고, 전부 **1차 전사를 그대로 두는** 쪽으로 고쳤다.

- 되풀이가 오디오 전체면 자를 자리가 없어 빈 `-segment_times`가 ffmpeg에 넘어갔다.
  ffmpeg가 죽고 그 실행의 **모든** 되풀이가 접혔다. → 자를 자리가 없으면 원본이 곧
  그 조각이다(`make_chunks`와 같은 처리).
- 조각 수와 구간 수가 어긋나면 순서로 짝지어 남의 오디오를 갈아끼웠다. → 어긋나면
  재전사를 건너뛴다.
- 낡은 픽스처의 오프셋을 "가장 가까운 조각"에 무조건 붙였다. 900초 떨어진 응답도
  붙었다. → 조각 길이를 넘게 떨어진 응답은 버린다.

### 기계 검사가 헛돌고 있었다

`check_repair_stays_upstream`이 정규식으로 import를 세고 있었는데, **이 프로젝트가
가장 많이 쓰는 형태**(`from . import log, refine, transcribe`)를 못 잡았다. 검사는
초록인데 선은 이미 넘어가 있을 수 있는 상태였다. `ast`로 파싱하게 고쳤고,
`check_verify_cannot_touch_output`도 같은 구멍이 있어 함께 고쳤다.

### 임계값

| 값 | 출처 |
|---|---|
| `loop_compression_ratio = 2.4` | whisper 레퍼런스 구현의 `compression_ratio_threshold` |
| `loop_ratio_window_words = 60` | 실측. 정상 최대 2.01 / 되풀이 최소 3.01로 갈린 창 |
| `chunk_max_seconds = 600` | D13. 바이트로 옮겼다가(D25) 다시 초로 되돌렸다 |
| `repair_temperature = 0.4` | 근거 없음. 1차(0.0)와 달라야 한다는 것만 확실하다 |
| `repair_margin = 2.0` | 근거 없음. 경계에서 어절이 잘리지 않을 만큼 |
| `repair_min_seconds = 3.0` | 근거 없음. 짧은 맞장구까지 결제하지 않으려는 하한 |
| `loop_repetitive_share = 0.5` | 근거 없음. 절반 넘게 되풀이면 회복 실패로 본다 |

`repair_*`와 `loop_repetitive_share`는 회차별 조정 대상이다. 바꾸면 여기에 남긴다.

### 포기하는 것 (정직하게)

- **회복 못 한 구간은 자막이 빈다.** 규칙 9의 예외이고, 이 결정의 진짜 대가다.
- **재전사 호출이 죽으면 그 구간은 접힌다.** 네트워크 사고가 자막 손실로 이어질 수
  있다. `--no-repair`가 탈출구다.
- **`zlib`을 쓴다.** 의존성은 늘지 않지만(표준 라이브러리) 규칙 10이 예시로 든
  목록에는 없던 모듈이다. whisper와 **같은 자**로 재려면 이것이어야 한다.
- **재전사가 원본보다 짧게 돌아올 수 있다.** 구간을 다 다시 물었어도 모델이 한 문장만
  주면 그 구간은 그만큼 빈다. 판정은 `replaced`이고, 로그가 `10장이 1장이 됐다`로
  숫자를 드러낸다 — 임계값으로 막지는 않는다. 모델의 답을 우리가 되돌릴 근거가 없다.
- **`cut_spans`는 오디오 전체를 한 번 더 복사한다.** `-c copy`라 CPU는 싸지만 디스크는
  쓴다(77분이면 약 37MB). 필요한 조각만 남기고 지우지 않는다 — 캐시 폴더 안이고,
  `make clean`이 치운다.
- **접힌 구간은 되돌릴 수 없다.** `redo`는 골격에서 다시 조판할 뿐이고, 골격에는
  이미 접힌 결과가 들어 있다. 원본이 필요하면 `--no-repair`로 다시 돌려야 한다.
- `TRACE_VERSION` 7.0 — 옛 `trace.json`은 읽히지 않는다.

### 남은 위험

재전사도 되풀이에 빠지면 접기로 간다. 그 구간의 실제 발화는 영영 자막에 안 들어간다.
심판 모델이 "말이 있다"고 했는데 접힌 구간이 로그에 자주 뜬다면
`repair_max_attempts`를 올리거나 `chunk_max_seconds`를 더 낮춰야 한다는 신호다.

## D28. 되풀이를 **막는** 층을 만들었다 (D27은 치우기만 했다)

D27을 넣고 사람이 문제 영상(4598초)을 재실행했다. 설정은 닿았고 조각도 짧아졌는데
되풀이는 그대로였다.

```
조각 8개 · 가장 긴 조각 9.7분        ← D27의 1·2번 원인은 해결됐다
1차 전사 2180개 세그먼트
되풀이 8구간 1443초 — 다시 묻는다     ← 9.7분 조각에서도 영상의 31%가 되풀이
  ... 8구간 전부 "회복"으로 표시 ...
검증: 되풀이 5구간 114초              ← 114초가 경고 없이 SRT로 나갔다
```

1443초 → 114초로 92% 줄었지만 0이 아니었다. **D27은 되풀이를 치우는 층이었고,
만들어지지 않게 하는 층은 없었다.**

### 되풀이는 온도 0의 산물이고, 창 사이를 타고 번진다

`tests/fixtures/api/fr_day_1_2_fhd.whisper.json`(같은 영상)을 whisper가 응답에 실어
보낸 `seek`(30초 디코딩 창)별로 묶으면 병리가 그대로 보인다.

```
seek=4057.8  cr=15.65  lp=-0.19  '여기가 보통은 여기가 보통은 여기가 보통은 …'
seek=4087.8  cr=12.04  lp=-0.21  '보통은 보통은  보통은 보통은 …'
seek=4117.8  cr=15.65  lp=-0.24  '여기가 보통은 …'
…  30.0초씩 정확히 전진하며 15개 창 연속
seek=4505.2  cr= 2.08  lp=-0.34  '내려오기가 힘들겠는데? …'   ← 448초 만에 탈출
```

- whisper는 창의 디코딩 결과를 **다음 창의 prompt로 넣는다**(`condition_on_previous_text`).
  그 글자가 되풀이면 다음 창도 되풀이다. **되풀이가 번지는 통로가 그것 하나뿐이다.**
- 방아쇠는 **창 경계에서 잘린 말**이다. 위 구간 직전 창의 끝이
  `'…아페로 할 때 먹는 메뉴들이 많아서 여기가 보통은'` — 잘린 조각 `'여기가 보통은'`이
  그다음 448초의 씨앗이 됐다.
- 레퍼런스 구현에는 탈출구가 둘 있다. `compression_ratio > 2.4`면 온도를 올려
  재디코딩하고, **온도가 0.5를 넘으면 직전 글자를 넘기지 않는다**:

  ```python
  if not condition_on_previous_text or result.temperature > 0.5:
      prompt_reset_since = len(all_tokens)
  ```

- **호스팅 API는 그 재디코딩을 하지 않는다.** 실측: `cr > 2.4`인 세그먼트 676개
  **전부** `temperature: 0.0`이고 `avg_logprob`가 −0.09 ~ −0.38이다. 되풀이에 빠진
  whisper는 확신에 차 있어서, 로그 확률로 발동하는 자동 폴백이 원리적으로 못 뜬다.

그런데 우리는 **1차 전사를 온도 0으로 부르고 있었다.** 되풀이가 가장 잘 나는 설정이다.
그러고는 재전사에서 온도 0.4로 다시 물어 1443초를 114초로 줄이고 있었다 —
병을 만들어놓고 고치는 중이었다.

### 세 겹으로 막는다

| 겹 | 값 | 성격 |
|---|---|---|
| `transcribe_temperature` 0.0 → **0.6** | 창 사이 조건을 끊는다 | **예방.** 번지는 경로가 사라진다 |
| `chunk_max_seconds` 600 → **180** | 호출이 바뀌면 반드시 끊긴다 | **상한.** 되풀이 최대 길이 = 조각 길이 |
| 재전사 개선 | 짧게·뜨겁게 다시 묻는다 | **잔불 정리** |

**온도 0.6**인 이유는 레퍼런스가 조건을 해제하는 경계가 0.5이기 때문이다. 0.2·0.4는
greedy에서만 벗어날 뿐 통로가 그대로 살아 있다. 대가는 **비결정성**이다 — 같은 영상이
실행마다 조금 다르게 나온다. 그리고 온도 0일 때만 도는 호스팅 폴백을 잃지만, 그건
이 병리에 안 듣는 것이 위 실측으로 확인됐다.

**조각 180초**인 이유는 조각 길이가 곧 되풀이가 자랄 수 있는 최대 길이이기 때문이다.
되풀이는 한 API 호출 안에서만 번지므로 호출 경계가 유일한 강제 리셋이다. 같은 픽스처
에서 조각 1은 새로 시작한 뒤 **1585초 동안 깨끗했다** — 리셋에는 실제로 값이 있다.
77분 영상이 8조각 → 26조각이 된다. whisper·gpt 모두 분당 요금이라 **총비용은 같다.**
느는 것은 요청 수(52건)와 경계 수(25곳)뿐이고, 경계는 이미 가장 조용한 지점으로 옮겨진다.

`vlogsrt.toml`의 `chunk_max_bytes = 4_800_000` 줄은 **지웠다.** D26 시절 길이를 대신
몰던 대리 변수인데 이제 초 한도가 언제나 먼저 걸린다(26조각 vs 8조각). 남겨두면
"설정이 안 닿았나"를 두 곳에서 의심하게 된다.

### 재전사가 병을 재현하고 있었다 — 잔존 114초의 주범

`preprocess.cut_spans`는 되풀이 구간을 **통째로 한 조각**으로 만들었다.
`chunk_max_seconds`가 거기엔 안 걸렸다.

| 재전사 구간 | 길이 |
|---|---|
| 674~1164초 | **490초** |
| 1336~1726초 | **390초** |
| 4244~4611초 | **367초** |

픽스처로 `repair.plan_spans`를 돌리면 **573초·536초**짜리 계획이 나온다. 1차 조각과
같은 길이의 오디오를, 이미 무너진 바로 그 오디오로 다시 물었다.

고친 방법은 **계획을 쪼개는 것 하나**다. `_plan`이 `owned` 세그먼트를 걸으며 누적
길이가 `repair_chunk_seconds`(120초)를 넘으면 계획을 하나 더 만든다. 하류
(`_cut`·`_rescue`·`_assemble`·`_disjoint`)는 한 줄도 안 바뀌었다 — 이미 계획 단위로
돌고 있었고, **계획이 곧 조각이고 곧 판정 단위**이기 때문이다.

**경계는 언제나 세그먼트 경계다.** 임의 시각에서 자르면 걸치는 세그먼트가 생기고,
앞 계획은 갈리고 뒤 계획은 유지될 때 그 세그먼트의 꼬리가 조용히 사라진다 —
D27이 리뷰에서 잡은 H2/H3와 같은 사고다(규칙 9).

### 합격 기준이 구간이 길수록 느슨해졌다

`repetitive_share <= 0.5`는 **되풀이 시간 ÷ 구간 시간**이라 490초 구간은 245초까지
되풀이여도 합격했다. 로그에 남은 것들을 계산하면 전부 share 0.14~0.18 — 합격선의
3분의 1이다. 그렇게 통과한 되풀이는 손대지 않고 그대로 SRT로 갔다.

`repetition.repetitive_seconds`(순수 함수)를 더하고, 합격을 **둘 다 만족**으로 바꿨다:
비율 상한(`loop_repetitive_share = 0.5`) **그리고** 절대 상한
(`repair_residual_seconds = 10.0`). 남은 초는 구간 길이와 무관하다.

### 실패는 길이로 나눈다 — 접기는 긴 되풀이에만

| 그 계획의 되풀이 길이 | 처리 | outcome |
|---|---|---|
| ≥ `repair_collapse_min_seconds`(30초) | 첫 장만 남기고 비운다 | `collapsed` |
| < 30초 | 1차 전사를 그대로 두고 WARN만 | `kept` |

D27의 접기 결정은 **1658초짜리 사고를 겨냥한 것이지 10초짜리가 아니었다.** 재전사 뒤
남은 것들은 `'치즈'` 9회(10초), `'Oh my god'` 27회(56초), `'세컨'` 5회(14초)처럼
짧았고, 그중 일부는 실제 발화일 수 있다 — 사진을 찍으며 아홉 번 말한 '치즈'까지
지우면 **되풀이가 아닌 이유로 규칙 9를 어기는 셈**이다. `REPAIR_KEPT`는 D27부터
모델에 있었지만 쓰이지 않고 있었다.

### 보고가 정직하지 않았다

`_report`가 합격을 전부 `log.info`로 찍어서, 사람 눈에는 8구간 전부 "회복"이었다.
114초가 남은 사실은 한참 아래 검증 로그에서만 보였다. 고친 것:

- 합격이어도 남은 되풀이가 있으면 `log.warn`으로 초수를 찍는다
- `Repair.residual_seconds` → `trace.json`에 남는다
- `summarize`가 `회복 N · 접음 N · 유지 N · 남은 되풀이 N초` — **마지막 줄만 봐도
  "전부 회복"이 거짓인지 알 수 있다**

### 손대지 않은 것

- **검출 구간이 부풀어 오르는 것.** `_compression_runs`는 이웃 두 세그먼트가 둘 다
  `cr > 2.4`이면 무한히 이어붙이고, `cr`은 30초 창 하나의 값이라 그 창의 세그먼트
  20~30개가 같은 값을 달고 온다. 조각 경계도 못 막는다(676~1160초는 1145초 경계를
  넘어 이어졌다). **계획을 쪼개면 판정이 조각 단위가 되므로 피해가 없다.** 검출을
  좁히는 것은 놓치는 쪽 위험이 있어 근거 없이 건드리지 않는다.
- `verify.py`는 한 줄도 안 바뀌었다(규칙 5). `repair`는 여전히
  `refine`·`output`·`layout`·`verify`를 import하지 않는다.
- `verify_chunk_sim_floor = 0.80`. 실행 로그에서 8조각 중 7개가 걸렸는데,

  어렵다. 0.76/0.77/0.79/0.80은 임계값 문제로 보이고
  **0.12(조각 7)·0.59(조각 1)·0.64(조각 6)만 진짜 신호**다 — 셋 다 되풀이가 남은

### 포기하는 것 (정직하게)

- **자막이 결정적이지 않다.** 온도 0.6은 샘플링이다. 같은 영상·같은 설정이 실행마다
  조금 다른 자막을 낸다. `make eval`은 픽스처를 읽으므로 여전히 결정적이다.
- **깨끗한 발화의 정확도가 조금 내려간다.** 레퍼런스가 이 온도를 폴백에만 쓰는 이유다.
  되풀이가 영상의 31%를 먹는 것과 맞바꿨다.
- **요청이 3배 는다.** 77분에 26조각 × 2모델 = 52건. 비용은 같지만 rate limit에
  더 가까워진다. `api_max_retries`가 받아낸다.
- **경계가 25곳이다.** 조각 경계마다 어절이 잘릴 수 있다. 가장 조용한 지점으로
  옮기지만 완전하지는 않다.
- **`kept`는 되풀이를 그대로 내보낸다.** 짧은 되풀이를 지키려고 연 문이고,
  `남은 되풀이 N초`가 그 값을 드러낸다.
- `TRACE_VERSION` 8.0 — 옛 `trace.json`은 읽히지 않는다.

### 남은 위험

온도 0.6이 실제로 창 간 조건을 끊는지는 **호스팅 구현에 달렸다.** 레퍼런스와 같다면
되풀이가 창 하나(30초)를 넘을 수 없다. 그래서 다음 실행의 결정적 확인은
**`되풀이 N구간` 중 30초를 넘는 것이 하나라도 있는가**다. 있으면 호스팅이 레퍼런스와
다르게 동작하는 것이고, 그때는 `chunk_max_seconds`를 더 낮추는 쪽으로 간다.

## D29. 되풀이가 **한 글자**로 오면 아무도 못 봤다 (2026-08-18)

D28을 넣고 사람이 문제 영상(4598초)을 재실행했다. **온도 0.6은 들었다.**

| S7 (온도 0.0) | 이번 (온도 0.6) |
|---|---|
| 되풀이 8구간 1443초 (영상의 31%) | 3회 이상 이어지는 동일 텍스트 런 **1개** |

| 마지막 27분이 통째로 한 문장 | 4400~4598초 전부 정상 발화 |

D28의 결정적 확인(창 간 조건이 끊겼는가)은 **통과다.** 그런데 사람이 SRT에서
이런 것을 찾아왔다.

```
27  00:01:23,940 --> 00:01:25,860   S
28  00:01:25,940 --> 00:01:28,060   F
29  00:01:28,140 --> 00:01:30,260   S
30  00:01:30,340 --> 00:01:32,260   F
...
70  00:02:50,340 --> 00:02:52,090   F     ← 44장, 88초
```

**84~172초, 44장이 전부 한 글자였고, 경고가 하나도 없었다.**

### 그 자리는 온도와 무관하게 무너지는 자리다

- 앞 큐가 `'세컨드'`(79.9초) · `'세컨드가 뭐죠?'`(81.9초)이고, S7(온도 0.0) 로그의
  잔존 되풀이 목록에 **`'세컨' ×5`**가 있었다. **같은 자리다.**
- 뒤 큐가 `'한국과는 다른 점. 예쁜 차가 없어요'`(172.2초) — 주행 구간이다.
- 온도가 바꾼 것은 **무엇으로** 무너지느냐뿐이다. 0.0에서는 앞 창의 글자(`'세컨'`)를
  물고 늘어졌고, 0.6에서는 그 통로가 끊긴 대신 창마다 따로 저확률 단일 토큰을 골랐다.
- 88초는 30초 창 **3개**다. 창을 타고 번진 모양이 아니라 **창마다 독립으로** 무너진
  모양이며, 조각 경계(180초)에 닿기 8초 전에 스스로 끝났다.
  → **`chunk_max_seconds`를 더 낮춰도 이건 안 없어진다.** D28이 남긴 판단 기준
  (30초 넘는 되풀이가 있으면 조각을 더 낮춘다)은 이 경우에 맞지 않는다.
- 곁증거: `language="ko"` 요청에 라틴 한 글자가 나온 것 자체가 분포 밖 신호이고,
  세그먼트가 1.83~2.20초 등간격(대부분 정확히 2.00초)이다 — 말을 따라간 경계가 아니다.

### 검출기 셋이 1글자에 나란히 눈이 멀었다

SRT의 시각에서 whisper 세그먼트 45개를 되짚어(`lead_in` 0.1 / `lead_out` 0.3 /
`min_gap` 0.08 역산) 실제 코드에 넣어봤다.

| | 무엇이 막았나 | 실측 |
|---|---|---|
| `_echo_runs` | **`loop_min_chars = 2`** — 1글자 런은 통째로 버려진다 | `find_repeats` → **`[]`** |
| `_compression_runs` | whisper의 `compression_ratio`는 그 30초 창의 **글자 수**로 갈린다 | `'F '` 10회=1.58 · 15회=**2.42** · 20회=3.00 (임계값 2.4) |
| `verify._check_cues` | `verify_short_cue_chars = 4` — 1글자 큐는 의심 후보에서 제외 | 44장 전부 조용 |

- 같은 런의 글자만 `'치즈'`로 바꾸면 **echo로 잡힌다.** 되풀이의 심각도가 아니라
  **글자 수**가 판정을 정하고 있었다.
- 압축률이 임계값에 걸터앉는 이유는 zlib 헤더 11바이트다. 1글자 되풀이는 30초 창에
  15개밖에 안 들어가서 텍스트가 29바이트다.
- 재전사는 `find_repeats`가 짚은 자리만 본다(`repair._plan`). 그래서 **한 번도 안 돌았다.**
- 조판은 결백하다. SRT의 시각을 `refine`에 넣어 **밀리초까지 재현**했다. 2초·1글자
  큐는 `min_duration`(0.85)을 넘어 병합 대상이 아니고 32자를 안 넘어 분할 대상도
  아니다. 정상 큐로 보이는 것이 맞다.

**규칙 9의 거울상이다.** "조용히 사라지는 구간은 없다"를 지켜왔는데, 조용히
**생겨나는** 구간이 있었다.

### 고친 것 — 세 번째 신호. 임계값은 하나도 안 바꿨다

`loop_min_chars`를 두 검출기의 **경계선**으로 쓴다. 2글자 이상은 메아리가, 그 아래는
낱자가 받는다. 빈틈도 겹침도 없다.

```python
def _letter_runs(spine, cfg):
    def both_letters(earlier, later):
        return _is_letter(earlier, cfg) and _is_letter(later, cfg)
    return [_to_repeat(run, WHY_LETTER, _key(run[0]))
            for run in _runs(spine, both_letters)
            if _is_letter(run[0], cfg) and _qualifies(run, cfg)]

def _is_letter(segment, cfg):
    return 0 < len(_key(segment)) < cfg.loop_min_chars
```

**글자가 달라도 한 런이다.** 실측의 앞머리가 `S F S F S F`였는데, 글자가 같기를
요구하면 런이 매번 끊겨 그 10초를 놓친다.

| | 결과 |
|---|---|
| 그 구간(45 세그먼트) | **84.04~172.15초, 44회** 한 구간으로 짚는다 |
| 온도 0.0 실측 픽스처 (1479 세그먼트·77분) | 오검출 **0건** |

오검출이 0인 이유: 그 픽스처의 1글자 세그먼트는 12개뿐이고(`'음'`,`'아'`,`'응'` 같은
감탄사) **인접한 쌍이 하나도 없다.** 완성된 SRT에서도 1글자 큐 3연속 런은 그 구간
하나뿐이다. `loop_min_chars = 2`가 경계로 정확히 맞는다 — `2글자 이하`로 넓히면
`['대박','와','오빠','어']` 같은 진짜 발화가 3건 걸린다. 이 회귀는
`test_the_real_first_pass_has_no_letter_runs`가 실측 픽스처로 지킨다.

`loop_min_chars = 1`로 낮추는 대안은 택하지 않았다. 뒤쪽 39장(78초)만 짚고 앞머리
5장(10초)을 놓치며, 메아리의 뜻을 바꿔 `'네 네 네'`까지 데려온다.

그 뒤는 이미 있는 길을 탄다. **`repair`는 한 줄도 안 바뀌었다** — 계획·조각·심판·
판정·보고가 전부 `find_repeats`에 대해 일반적이다. `_recovered`도 같은 함수를 쓰므로
**다시 물어 또 낱자를 받으면 회복 실패로 잡힌다.** 88초 ≥ 30초라 접힌다.

### 심판이 빈 답을 주면 "말이 있다"로 읽고 있었다

```python
not repetition.looks_repetitive("", cfg)   # → True = "되살릴 말이 있다"
```

빈 글자는 되풀이가 아니라서 그렇게 읽힌다. 이번 태스크가 노이즈 구간을 처음으로
재전사 경로에 넣기 때문에 지금 드러났다 — 그대로 두면 그런 구간마다 더 뜨거운
whisper 호출을 한 번씩 사게 된다. `_heard_speech`가 글자가 있는지부터 본다.

`Repair.verdict`의 문구도 `'심판: 되풀이가 맞다'` → **`'심판: 되살릴 말이 없다'`**로
고쳤다. 심판이 답한 것은 "되살릴 말이 있나" 하나이고, 아니라는 답에는 되풀이만
들린 경우와 아무 글자도 없는 경우가 섞여 있다. 둘 다 "더 살 이유가 없다"로 같다.

### 손대지 않은 것

- **`verify_short_cue_chars = 4`.** 검출이 보게 되면 되풀이로 뜬다. 짧은 큐를 전부
  의심으로 올리면 로그가 못 쓰게 된다.
- **`no_speech_prob`으로 "여긴 말이 아니다"를 판정하는 것 — 규칙 4.** 되살릴 말이
  있는지는 심판이 듣고 정한다.
- **`chunk_max_seconds`·`transcribe_temperature`.** 위의 분석대로 둘 다 이 병리의
  원인이 아니고, 온도 0.6은 이번 실행이 효과를 증명했다.
- **`TRACE_VERSION`은 8.0 그대로.** 필드가 늘지 않고 `Repeat.reason`의 값 하나가
  늘 뿐이다. 올리면 사람이 가진 기존 `trace.json`의 `redo`가 깨진다.
- **`verify_chunk_sim_floor = 0.80`** — D28에서 미뤄둔 그대로. 다만 이번 구간은
  조각 0(0~180초)의 절반이므로 조각 유사도가 이것을 짚었을 가능성이 크다.
  **유일하게 눈이 멀지 않았던 신호다.** 실행 로그를 봐야 확인된다.

### 남은 위험

**노이즈 구간의 재전사가 그럴듯한 헛소리를 돌려줄 수 있다.** `_recovered`는 결과가
되풀이가 아닌지만 보므로, whisper가 엔진음 88초에 대고 멀쩡해 보이는 문장을 지어내면
그대로 갈아끼운다. 44장의 `'F'`는 사람 눈에 즉시 쓰레기로 보이지만 지어낸 문장은
안 그렇다 — **더 나쁠 수 있다.**

이 위험은 D29가 만든 것이 아니고 D27부터 모든 되풀이 구간에 있었다(합격 기준이
"되풀이가 아니면 통과"다). 심판을 **합격의 문턱**으로 올리는 것이 대책이지만 근거와
결정이 따로 필요하다. 다음 실행의 84~172초에 지어낸 문장이 들어오면 그때 올린다.

## D30. 자막에 온점을 쓰지 않는다 — 조판 정리 계층 (2026-08-27)

whisper는 받아쓰기 모델이라 **문어체 부호를 그대로 실어 보낸다.** 실측 회차
(`fr_day_1_2_fhd`, 1479 세그먼트)의 SRT에 온점이 **642개** 있었다. 영화·방송 자막
관행은 반대다: 문장 끝에 마침표를 찍지 않고, 말줄임표는 `…` 한 글자이며, 같은 부호를
겹쳐 쓰지 않는다.

지금까지 파이프라인에는 **글자를 다듬는 계층이 아예 없었다.** `spine_to_cues`가
세그먼트 텍스트를 그대로 옮기고, `refine`은 자르고·합치고·시각만 만지며, `layout`은
줄만 나눈다. 그래서 부호가 끝까지 그대로 나갔다.

### 정한 것

`vlogsrt/polish.py` — `refine.refine()`의 **맨 앞**에서 도는 순수 함수 계층.

| # | 규칙 | 예 |
|---|---|---|
| 1 | 온점 2개 이상 → `…` 한 글자 | `그래서...` → `그래서…` |
| 2 | 같은 부호의 연속을 하나로 | `진짜!!!` → `진짜!` |
| 3 | 온점 삭제. **숫자 사이는 예외** | `왔습니다.` → `왔습니다` / `1.5초` 그대로 |
| 4 | 부호 앞 공백 제거, 뒤에 공백 하나 | `진짜 ?이제` → `진짜? 이제` |
| 5 | 큐 **끝**의 쉼표 제거 | `뭐냐면,` → `뭐냐면` |
| 6 | 공백 정규화 | |

**순서가 곧 규칙이다.** 1을 3보다 먼저 돌리지 않으면 말줄임표가 통째로 증발한다.
물음표·느낌표·문장 중간 쉼표는 **유지한다** — 뜻이 다르다. `?!`도 겹쳐 쓴 것이
아니므로 남긴다.

### 왜 `refine`의 맨 앞인가

- **진입점이 하나가 된다.** `run`도 `redo`도 UI도 전부 `refine.refine()`만 부른다.
- **분할보다 앞이어야 한다.** 부호를 지우면 글자 수가 줄어 `needs_split`의
  `max_chars_per_cue`·`max_cps` 판정이 바뀐다. 자른 뒤에 지우면 굳이 두 장일 필요가
  없던 큐가 두 장으로 남는다. 실측에서 큐가 1419장 → **1415장**이 됐다.

### 이 계층이 여는 선과, 대신 못 박은 것

규칙 5는 "출력을 바꾸는 곳은 재전사 하나뿐"이었다. 정리는 출력 **글자**를 바꾸므로
그 선을 한 뼘 연다. 대신 다섯을 못 박았다.

1. **글자를 지우지 않는다 — 문장부호만 지운다.** 실측 회차 전체에서 정리 켠 결과와
   끈 결과가 `strip_for_compare`로 **완전히 같다**(`test_invariants.py`). 이 등식이
   이 계층의 유일한 안전선이다.
2. **시각을 못 건드린다**(규칙 3). 실측에서 타임코드 줄이 한 줄도 안 바뀐다.
3. **큐를 비우지 않는다**(규칙 9). 정리 결과가 비면 원문을 그대로 되돌린다 —
   `'.'` 한 글자뿐인 큐가 조용히 사라지면 안 된다.
4. **골격을 안 건드린다**(규칙 2). 정리는 `spine → cues` 뒤에서만 돈다. `trace.json`의
   `spine[]`에는 언제나 부호가 살아 있는 원문이 남고, `redo --no-polish`로 되돌릴 수 있다.
5. `polish.py`는 `repair`·`repetition`을 모르고, `repair`·`verify`도 `polish`를 모른다.
   `check_invariants.py`가 양쪽을 검사하고, `polish.py`는 `PURE_MODULES`에 들어간다.

### 임계값

`polish_*` 여섯은 **외부 근거가 없는 조정 대상**이다(`cut_*`·`verify_*`·`repair_*`와
같은 부류). 지우는 부호 집합은 `particles`와 마찬가지로 임계값이 아니라 어휘이므로
config에 둔다. TOML로 덮어쓸 때는 **배열 형식을 써라** — `_coerce`가 문자열을 쉼표로
쪼개서 `polish_trailing_drop = ","`가 빈 튜플이 된다.

`TRACE_VERSION`은 8.0 그대로다. 필드가 늘지 않고 `Cue.flags`의 값 하나(`polished`)가
늘 뿐이라, 사람이 가진 기존 `trace.json`의 `redo`가 깨지지 않는다.

### 바꾼 계약 하나

`test_every_word_the_model_said_reaches_the_srt`가 모델이 말한 어절과 SRT 어절이
**부호까지 글자 그대로 같을 것**을 단언하고 있었다. `'왔습니다.'` → `'왔습니다'`가
되면 깨진다. 임계값이 아니라 이번에 바꾸는 계약 그 자체이므로 비교를 부호 제거 후로
바꿨다. **어절을 하나도 잃지 않는다는 보장은 그대로다** — 같은 파일의
`test_srt_text_is_exactly_the_spine_text`가 이미 그 방식으로 비교한다.

### 실측 (실측 픽스처 · API 호출 없음)

| | 정리 끔 | 정리 켬 |
|---|---|---|
| 온점 | 642개 | **0개** |
| 큐 | 1419장 | 1415장 |
| 16자 초과 줄 | 2줄 | 1줄 |
| 글자(`strip_for_compare`) | — | **완전히 동일** |
| 타임코드 | — | **완전히 동일** |

### 남은 위험

**약어와 도메인의 온점이 함께 지워진다.** `'a.m.'`·`'youtube.com'`처럼 숫자가 아닌
글자 사이의 온점은 예외 규칙에 걸리지 않는다. 브이로그 한국어 발화에서는 실측 642개
중 한 건도 없었지만, 회차에 따라 나올 수 있다. 나오면 예외를 숫자에서 "앞뒤가 모두
글자인 경우"로 넓히는 것이 대책이고, 그때 근거와 함께 정한다.

## D31. 짧은 큐가 한 줄을 못 채운 채 따로 선다 (2026-08-27)

D30을 넣고 실측 회차의 조판을 재보니, 큐 1415장 중 **7자 이하가 489장(35%)**이었다.
`'네'`·`'음'`·`'벨레'` 같은 한두 어절이 저마다 한 장씩 서서 화면이 깜빡이고, 한 줄
16자 중 절반도 못 쓰고 다음 장으로 넘어간다.

### 원인 — 병합이 **글자**가 아니라 **시간**만 봤다

`refine.can_merge`의 첫 줄이 `if first.duration >= cfg.min_duration: return False`였다.
병합이 원래 **깜빡임**을 없애려고 만들어진 장치라, 0.85초에 못 미치는 큐만 이웃과
합쳤다. 그래서 `'벨레'` 두 글자가 1.4초 동안 떠 있으면 — 깜빡이지는 않으니 —
글자가 아무리 짧아도 절대 합쳐지지 않았다.

### 정한 것 — 합칠 이유를 둘로 나눈다

| 이유 | 조건 | 허용 폭 |
|---|---|---|
| 깜빡임 없애기 (기존) | 앞 큐가 `min_duration`(0.85초)보다 짧다 | 두 줄 = `max_chars_per_cue`(32자) |
| **한 줄 채우기 (새로)** | 그 밖의 모든 경우 | 한 줄 = `max_chars_per_line`(16자) |

둘 다 `merge_gap`(0.4초) 안쪽일 때만이다. **새 임계값을 만들지 않았다** — 이미 있는
`max_chars_per_line`과 `merge_gap`을 쓴다. 한 줄을 넘겨가며 합치지 않는 이유는
간단하다: 한 줄을 넘긴다는 것은 두 장으로 둘 이유가 있다는 뜻이다.

**`max_duration` 검사를 함께 넣었다.** 없으면 병합이 분할을 되돌린다 — 길이 때문에
자른 큐를 도로 붙이고, 시간 보정이 `max_duration`에서 끝을 잘라내 뒷말이 화면에서
사라진다. 이 검사는 예전 경로의 결과를 바꾸지 않는다(실측 1415장 → 1415장 동일).

### 실측 (실측 픽스처 · API 호출 없음)

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 큐 | 1415장 | **1304장** |
| 7자 이하 큐 | 489장 (35%) | **318장 (24%)** |
| 큐당 평균 글자 | 11.3자 | **12.4자** |
| 큐당 평균 노출 | 1.81초 | **1.96초** |
| 2줄 큐 | 300장 | 299장 |
| 글자(`strip_for_compare`) | — | **완전히 동일** |
| 겹침·16자 초과 줄 | 0 · 1 | 0 · 1 |

**2줄 큐가 늘지 않는다**(300 → 299)는 것이 이 결정의 핵심이다. 한 줄 한도에서 멈추므로
합치기가 두 줄짜리 자막을 만들어내지 않는다.

### 하지 않은 것

- **앞줄을 16자까지 채우는 줄바꿈**(S12가 측정해 반대한 방향). 2줄 큐 300장 중 99장에서
  뒷줄이 4자 이하로 남고 1장은 3줄이 된다. 줄바꿈 자리는 지금의 가운데 균형 그대로다.
- **`merge_gap`을 넓히는 것.** 0.4초는 이어지는 말과 끊긴 말을 가르는 선이고, 넓히면
  앞 발화의 자막이 뒤 발화가 시작될 때까지 남는다.

### 남은 위험

병합은 두 발화를 한 장에 묶으므로 **앞 발화의 자막이 뒤 발화의 끝까지 떠 있다.**
사이가 0.4초 안쪽일 때만 하므로 이어지는 말일 가능성이 높지만, 화자가 빠르게 화제를
바꾸는 자리에서는 두 문장이 한 장에 얹힐 수 있다. 회차를 보고 답답하면 `merge_gap`을
줄이는 것이 먼저다.

## D32. 조각 꼬리 싱크 신고 — 자부터 고쳤다 (2026-08-28)

신고는 **"영상 조각 마지막 쪽에 가면 자막 싱크가 무너지고, 다음 조각에서 회복된다"**
였다. 이 형태 자체가 단서다. 오차가 **조각 안 위치의 함수**이고 경계에서 리셋된다는
뜻이라, 오프셋 계산이나 추출 경로 같은 전역 원인은 배제된다. D13이 같은 문장을 이미
적어두었다 — *"청크가 38분씩이라 디코더가 뒤로 갈수록 무너진다(청크1 실패는 전부 후반부)."*

**그런데 확정할 수가 없었다.** 이유 셋이 전부 도구의 문제였고, 이번에는 그것만 고쳤다.
**SRT 바이트는 변경 전후로 동일하다**(`feefb4bf…`, 픽스처 실행으로 확인).

### 1. 이 신고를 받으라고 만든 게이트가 죽어 있었다

`make verify`(= `scripts/verify_timing.py`)는 D13이 "다음에 같은 신고가 오면 귀로 듣지
말고 이걸 돌린다"며 만든 도구다. 검사 넷 중 실제로 도는 것은 하나였다.

| 무엇 | 어떻게 죽어 있었나 |
|---|---|
| 청크 정렬 | `{stem}.batch*.mp3`를 찾는데 `preprocess`는 `{stem}.chunk%04d.mp3`로 쓴다. 아무것도 못 찾고 **"단일 청크, 검사 생략" → 통과** |
| 길이 보존 | `out/<stem>/trace.json`을 보는데 실제 경로는 `out/trace.json`. `video=None`이 되어 영상↔오디오 비교가 사라진다 |
| SRT 커버리지 | 같은 이유로 파일을 못 찾고 **`passed=True`로 통과** |
| 골격 시각 | 유일하게 돌았다. 다만 **전역 시프트 하나**만 찾으므로 조각 안 드리프트는 원리적으로 못 본다 |

**건너뛴 것이 통과로 보인 것이 진짜 사고다.** 이제 `SKIP`으로 찍고 요약에 따로 센다.
조각 파일 이름은 `preprocess.chunk_template`/`chunk_glob` 한 곳에서만 나온다.

### 2. 자 자체에 결함이 둘 있었다

- **음의 지연을 못 봤다.** `full_env[max(0, lag):]`가 음수 지연을 전부 0으로 눌렀다.
  자막이 **빠른** 쪽으로 어긋난 경우를 볼 수 없는 자였다.
- **지연마다 비교 길이가 달랐다.** `correlation`이 짧은 쪽에 맞춰 자르므로, 참조가
  모자라는 지연은 더 적은 데이터로 더 높은 점수를 받는다. 이제 모든 지연이 같은
  길이를 비교하고, 탐색 범위는 양쪽 다 실제 오디오 안에 있게 대칭으로 잡는다.

그리고 조각을 **머리·가운데·꼬리 세 창**으로 본다. 예전에는 앞 60초만 봤다 —
문제가 난다는 꼬리를 애초에 안 보는 자였다.

### 3. 실행이 끝나면 조각 경계가 사라졌다

`Trace`에 조각 오프셋이 없었다. 조각 mp3는 캐시를 지우면 사라지므로, 실행 뒤에는
"어디서 잘렸나"를 알 방법이 아예 없었다. `ChunkMark`(`index`/`offset`/`duration`)를
더하고 `TRACE_VERSION`을 9.0으로 올렸다. **기록일 뿐 시각을 만들지 않는다**(규칙 1·2 무관).

### 새 검사 — 시각 붙음(glue)

포락선 자는 이 콘텐츠에서 무디다. 실측(제공된 77분 회차 + 원본 영상):

| 잰 것 | 결과 |
|---|---|
| 전역 최적 시프트 | 창마다 −2.0 ~ +1.8초로 흩어지고 F1 이득이 0.01 수준 |
| onset 대비 큐 시작 | 전체 중앙값 +0.05초. 일치율이 27~38%뿐이라 큰 붕괴는 못 본다 |
| 조각 머리 vs 꼬리 | 꼬리 38.0% vs 머리 38.5% — **무상관** |

그래서 오디오를 안 읽고 **whisper 응답의 시각 모양**을 보는 검사를 새로 넣었다.
`다음.start == 앞.end`인 비율 — whisper가 시각을 **재기를 그만두고 이어 붙인** 지문이다.
녹화 픽스처(조각 38분 시절)에서 골격 기준으로:

| 조각 안 위치 | 붙음 비율 (두 조각 합산) | `no_speech_prob` 중앙 |
|---|---|---|
| 0–10% | 5.1% | 0.150 |
| 30–40% | 19.4% | 0.021 |
| 60–70% | 31.2% | 0.094 |
| 90–100% | **47.3%** | 0.048 |

조각별로는 조각 1이 머리 3.6% → 꼬리 48.6%(상승 0.449), 조각 0은 18.5% → 38.5%
(상승 0.200)다. `GLUE_RISE_TOL = 0.25`가 둘 사이에 앉는다. **응답 세그먼트를 통째로
세면 다른 수가 나온다**(0.00 → 0.92) — 글자 없는 세그먼트가 골격에서 빠지면서 사슬이
끊기기 때문이고, 자막이 되는 것은 골격이므로 골격 기준이 옳다.

이 값은 **표시만 한다.** 되풀이 검출의 네 번째 신호로 넣지 않았다 — 그건 재전사를
돌리는 판정이라 규칙 4·9에 닿는다.

### 왜 아직 원인 확정이 아닌가

**손에 있던 산출물이 현재 파이프라인의 것이 아니었다.**

| 파일 | 정체 |
|---|---|
| `fr_day_1_2_fhd.srt` (8/17) | vlogsrt 출력. 다만 D28(조각 180초, 8/18) **이전**이라 조각이 8개(9.6분)였다. 지금 설정이면 26개(3분)다 |
| `fr_day_1_2_fhd_2.srt` (8/27) | 위 파일을 **Vrew로 불러들인 것.** 시작 시각이 같고 끝만 다음 큐에 붙였다. 독립 정답지가 아니다 |

그 SRT로는 조각 8개·26개 두 가설 모두에서 조각 안 위치별 차이가 없었다:
`min_gap` 지문(간격 == 0.080초) 비율 76~90% 무작위, 큐 사슬 길이 무상관.

부수 실측 하나: 그 SRT는 **간격의 84%(1418/1688)가 정확히 0.080초**다. `lead_in 0.1` +
`lead_out 0.3`이 큐마다 0.4초를 부풀려 실제 간격 0.4초 미만인 이웃을 전부 겹치게 만들고,
`resolve_overlaps`가 중점에서 갈라 `min_gap`으로 고정한 결과다. 사슬 271개, 최대
83큐·171초가 한 덩어리다. 시각이 붙은 큐는 refine이 **중앙값 +0.14초 늦게**, 정상 큐는
**−0.10초 빠르게** 민다. 조판 임계값은 이번에 **건드리지 않았다** — 원인 1을 재기 전에
조판을 손대면 무엇이 나아졌는지 못 가른다.

### 원인 후보 (측정으로 좁힌 상태)

| # | 후보 | 상태 |
|---|---|---|
| 1 | whisper의 조각 내 시각 열화. 창이 예측 타임스탬프만큼 전진하다 위상이 어긋나고 조각 끝까지 간다. 경계에서 `seek` 리셋 | **가장 유력.** 경계 리셋이라는 형태가 신고와 일치 |
| 2 | 조각 마지막 창의 무음 패딩 (실제 오디오가 30초에 못 미쳐 0으로 채워진다) | 유력. 조각 꼬리 전용 |
| 3 | 조각 경계가 말 한가운데 떨어진다. `cutpoints.quietest`에 무음 임계값이 없다(규칙 4를 지키느라 의도적) | 유력. D28이 경계를 8개→26개로 늘렸다 |
| 4 | 조판 계층의 부호 갈림 (+0.14 / −0.10초) | 확정. 크기가 0.24초라 단독 원인은 아니다 |
| 5 | **마지막 조각이 0.2초 밀린다** (`split_at`) | **확정** — 아래 절. 다만 조각 **하나**만 설명한다 |
| 6 | 전역 오프셋·추출 경로 | **배제** (D13 + 이번 onset 실측) |

### 되살린 게이트가 곧바로 짚은 것 — **마지막 조각이 0.2초 밀린다**

게이트를 살리자마자 새 결함이 나왔다. **API를 부르지 않고** 실제 77분 오디오로 확인했다
(영상에서 오디오만 뽑아 `split_at`을 돌리고 포락선을 대조했다).

`-f segment -c copy`가 만든 조각 중 **마지막 것만 CSV `start`보다 +0.2초 늦게 시작한다.**

| 실측 | 결과 |
|---|---|
| 실제 오디오, 조각 2개 | 조각 0 지연 +0.0 (상관 1.0000) · **조각 1 지연 +0.2** (머리·가운데·꼬리 세 창 모두) |
| 실제 오디오, 조각 6개 | 조각 1~4 전부 **+0.0** · **마지막 조각만 +0.2** |
| 같은 오프셋(2299초)이 내부일 때 | **+0.0** — 자른 위치의 문제가 아니라 **마지막이라는 것**의 문제다 |
| 합성 오디오, 자를 자리 4가지 | 전부 마지막 조각만 +0.2 재현 |
| 빠른 탐색(`-ss` 앞) vs 정확 탐색(`-ss` 뒤) | **같은 값** — 탐색 오차가 아니다 |
| 디코딩되는 길이 | 마지막 조각이 CSV보다 **0.262초 짧다**. 다른 조각은 0.069초(통상 디코더 지연) |

조각 0은 경계 **직전**까지 상관 1.0000인데 조각 1은 시작부터 어긋난다. 즉 마지막 조각의
오디오 0.2초가 사라졌고, 그만큼 조각 좌표가 원본 좌표와 어긋난다.

**결과: 마지막 조각의 자막이 통째로 약 0.2초 빠르다.** 지금 설정(조각 26개)이면 영상의
마지막 3분, D28 이전(조각 8개)이면 마지막 9.6분이다. D13이 "전 조각 일치"를 봤던 것은
그때 자가 조각 **앞 60초만** 봤고 조각 수가 4개였기 때문이 아니라, 그 표가 어느 조각을
봤는지 지금 확인할 수 없기 때문이다 — 지금 자로는 재현된다.

**고치지 않았다.** 오프셋을 건드리면 SRT가 바뀌고, 그건 이 태스크의 범위(진단) 밖이다.
왜 마지막 조각에서만 나는지도 아직 모른다. 다음 태스크다.

### 남은 위험

- `GLUE_RISE_TOL = 0.25`의 근거가 **회차 하나 · 조각 둘**이다. 실제 회차에서 오검출이
  나면 조정 대상이다(검증 도구의 판정 기준이지 파이프라인 임계값이 아니다).
- 붙은 시각이 **언제나 나쁜 것은 아니다.** 쉼 없이 이어지는 말은 실제로 붙어 있다.
  이 검사는 "조각 안에서 **오르는가**"를 보므로 절대 수준이 아니라 기울기를 본다 —
  그래도 말이 뒤로 갈수록 빨라지는 회차에서는 오검출이 날 수 있다.
- 조각 경계 기록은 `--offline` 실행에서 비어 있다(메타 픽스처에는 오디오가 없다).
  그때는 응답 오프셋으로 되짚는다 — 조각이 빈틈없이 덮으므로(규칙 4) 추정이 아니다.

## D33. `lead_out`이 없는 무음을 만들어 뒤 큐를 민다 (2026-08-31)

"자막 시작이 0.3초씩 늦는다"는 신고. D32가 원인 후보 **4번(확정, 0.24초)** 으로 적어
두고 태스크를 내지 않은 항목이다. 유료 호출 없이 픽스처만으로 재현·수정했다.

### 무엇이 일어나고 있었나

`refine.adjust_timing`이 `lead_out = 0.3`을 **무음이 있든 없든** 모든 큐의 끝에 붙였다.
whisper는 세그먼트를 **간격 0으로 붙여** 내놓는다 — 77분 픽스처에서 경계 1930곳 중
375곳이 정확히 0이고, 0.08초 미만이 33곳 더 있다(D32의 「시각 붙음」이 재는 바로 그것).
그래서 앞 큐의 꼬리가 뒤 큐의 머리를 덮고, `resolve_overlaps`가 그 겹침을 **중점에서
갈라** 뒤 큐의 시작을 뒤로 민다.

```
앞.end + lead_out(0.3)   과   뒤.start − lead_in(0.1)   의 중점 + min_gap/2
  = 뒤.start + 0.1 + 0.04
  = 뒤.start + 0.14
```

`min_duration` 확장도 같은 죄를 지었다. `end = start + 0.85`가 다음 큐의 시작을 따지지
않고 늘어나, 짧은 큐 뒤에서 같은 충돌을 한 번 더 만들었다.

**실측 (77분 회차, 큐 머리 1086개 · 같은 골격에 옛 함수와 새 함수를 나란히 태웠다)**

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 늦은 큐 | **262개 (24.1%)** | **2개 (0.2%)** |
| `+0.14초` 무리 | **184개** | **0개** |
| 정확히 `0.00초` | 16개 | **198개** |
| `−0.10초`(정상) | 774개 | 853개 |
| 중앙값 | −0.100초 | −0.100초 |
| 큐 수 · 줄 · `seg_ids` | — | **전부 동일** (시각만 527장 이동) |

산수와 실측 최빈값이 소수점까지 맞는다. 추측이 아니다.

### 어떻게 고쳤나

`lead_in`/`lead_out`이 **실제로 있는 무음만** 먹게 했다. 없는 무음을 만들어 이웃을
밀지 않는다. 헬퍼 셋(`_lead_in_room`·`_lead_out_room`·`_stretch_ceiling`)이 이웃과의
간격에서 한도를 한 번 더 깎는다.

무음이 모자라면 **`lead_in`이 먼저 가져간다.** 말이 시작되는 시각은 사실이고 꼬리
연장은 편의다. 순서를 뒤집으면 고치려던 결함이 그대로 돌아온다.

**규칙 3을 더 좁게 지키는 변경이다.** 시각을 움직이는 곳은 여전히 `refine` 하나이고,
이동량은 여전히 `lead_in`/`lead_out`/`min_gap`/`min_duration`/`max_duration` 안이다.
새 임계값은 하나도 만들지 않았다(규칙 8).

### 손대지 않은 것과 그 이유

- **`resolve_overlaps`의 중점 규칙.** 겹침이 whisper 원본에서 온 진짜 겹침일 때는
  중점이 옳다. 위 수정으로 이 함수가 받던 **가짜 겹침** 자체가 사라진다.
- **`lead_in`·`lead_out` 값.** `lead_in`을 키우면 붙은 큐에는 효과가 없고 정상 큐만 더
  당겨져 편차가 오히려 벌어진다. 값이 아니라 적용 조건이 틀렸던 것이다.
- **남는 큐 2장.** whisper가 **0.02초짜리** 세그먼트를 냈고, `min_gap`을 양쪽에서
  떼낼 수 없어 `resolve_overlaps`가 뒤 큐를 민다. 앞 큐의 시작을 더 당겨야 풀리는데
  그건 규칙 3의 `lead_in` 한도를 넘는다. 0.2%를 위해 규칙을 열지 않는다.

### 게이트가 이걸 못 보고 있었다

D32가 살려 놓은 검사 다섯은 **전부 골격만** 본다. 조판 계층이 시각을 미는 결함은
`make verify`에 한 번도 잡히지 않았다. `check_glue`와 같은 부류 — **오디오를 읽지 않고
`trace.json`만 읽는 순수 계산** — 으로 「조판 지연」 검사를 넣었다.

| 값 | 근거 |
|---|---|
| `LAG_LATE_TOL_S = 0.02` | 반올림 잡음 여유. 이보다 늦으면 "늦었다"로 센다 |
| `LAG_LATE_RATE_TOL = 0.05` | 실측. 고치기 전 24.1% / 고친 뒤 0.2%. 0.05가 둘 사이에 앉는다 |

한 세그먼트를 여러 큐가 나눠 가질 때는 **첫 큐만** 센다. 분할된 뒤쪽 조각은 원래
늦는 게 맞아서, 같이 세면 결함이 정상에 묻힌다.

### 남은 위험

- **이 회차의 지연이 전부 조판 탓은 아니었다.** 같은 실행에서 「청크 정렬」의 마지막
  조각은 여전히 +0.2초(S17), 「시각 붙음」은 조각 0이 머리 8% → 꼬리 39%로 오른다
  (D32 원인 1~3). 둘 다 whisper·ffmpeg 쪽이고 유료 재실행(S16)이 있어야 잰다.
  **조판 갈림이 사라졌으므로 다음 재실행에서 남는 지연은 그쪽 것이다.**
- `LAG_LATE_RATE_TOL`의 근거가 **회차 하나**다. `GLUE_RISE_TOL`과 같은 처지이고,
  검증 도구의 판정 기준이지 파이프라인 임계값이 아니다.

## D34 — 비전 판정 모델을 Gemini로 바꾼다 (2026-09-13)

러프컷의 **6단계 비전 판정**(블록 프레임을 보고 남길 후보를 고르는 곳)의 기본
공급자를 z.ai `glm-5.3-flash`에서 Google `gemini-3.8-flash`로 바꾼다.

### 왜 바꿀 수 있었나 — 의존성이 늘지 않는다

Gemini는 **OpenAI 호환 엔드포인트**(`https://generativelanguage.googleapis.com/v1beta/openai/`)
를 제공한다. `vlogsrt/transcribe.py`의 `create_vision_client`는 이미
`openai.OpenAI(api_key=…, base_url=…)` 하나로 되어 있고 환경을 스스로 읽지 않는다 —
**base_url·키·모델명만 바뀐다.**

- 불변 규칙 10(의존성 `openai`·`tomli-w`·`rich`) 그대로.
- 계약 §4(openai import는 `vlogsrt/transcribe.py` 정확 경로 하나) 그대로.
- `build_payload`가 내는 `image_url` + `data:image/…;base64,`를 호환 레이어가 받는다.
- STT 자격증명과 분리되는 선도 그대로 — `_STT_CREDENTIAL_ENV_NAMES` 재사용 금지가
  `GOOGLE_API_KEY`에도 그대로 적용된다.

### 바꾼 값

| 필드 | 전 | 후 |
|---|---|---|
| `vision_model` | `glm-5.3-flash` | `gemini-3.8-flash` |
| `vision_api_key_env` | `ZAI_API_KEY` | `GOOGLE_API_KEY` |
| `vision_base_url_env` | `ZAI_BASE_URL` | `GEMINI_BASE_URL` |

`gemini-2.5-flash`는 2026-10-16 종료 예정이라 기본값 후보에서 제외했다. 더 싼
`gemini-3.5-flash-lite`도 쓸 수 있다 — 블록 하나당 이미지 16장이라 전체 비용 차이가
영상 한 편에 몇십 센트 수준이어서 **판정 정확도를 택했다**. 바꾸려면
`vlogsrt.project.toml`의 `vision_model` 한 줄이다.

### 난간은 좁히지 않았다

`check_no_hardcoded_model`의 `PROJECT_MODEL_LITERAL`을 `glm-`에서
`(?:glm|gemini)-`로 **넓혔다.** glm을 빼지 않은 이유: 쓰지 않게 된 접두사를 지우면
되돌리기가 조용히 커밋된다. 이 검사는 "지금 쓰는 모델"이 아니라 **"코드에 박힌 모델
이름"**을 막는 것이다. 넓히지 않았다면 `"gemini-3.8-flash"`를 아무 파일에나 박아도
검사가 못 잡았을 것이다 — 공급자 교체가 난간을 조용히 없앨 뻔한 자리였다.

### 확인하지 못한 것

- **실제 계정의 Gemini 비전 능력·응답 형태·단가.** `glm-5.3-flash`도 같은 상태로
  남아 있었다(기준 명세: *"live account capability not yet tested"*). 유료 호출은
  사람이 한다.
- 호환 레이어가 16장 동시 입력과 구조화 JSON 응답을 우리 스키마대로 내는지.
  `parse_decision`의 엄격한 거부 경로가 이 미검증을 fail-closed로 받는다.

### 하지 않은 것 — 네이티브 비디오 입력

Gemini는 영상을 그대로 받을 수 있고, 그러면 기준 명세가 스스로 인정한 약점
(*"Sparse images not proof of motion/blur/no speech"*)이 사라진다. 이번에는 **하지
않았다.** 영상에는 오디오가 딸려 오는데, 불변식 20번이 "제거 계층은 오디오를 듣지
않는다"이다. 모델이 소리를 듣고 "여긴 말이 없으니 잘라도 된다"고 하면 **모델이
오디오로 제거 권한을 만드는 것**이고, 제거 권한은 가드에서만 나온다. 하려면 오디오를
벗기고 `request_sha256`을 프레임 목록이 아니라 클립 바이트로 다시 정의해야 한다 —
P5-04·P5-05·P6-01의 재설계다. 별도 판단으로 남긴다.

## D35 — 컷을 먼저 하고 자막을 나중에 만든다. 규칙 4·9를 그만큼만 연다 (2026-09-13)

파생 계층(`vlogsrt/project/`)의 순서를 **자막 → 컷편집**에서 **컷편집 → 자막**으로
뒤집는다. 사람이 편집하는 순서와 같아지고, 자막이 최종 편집본을 설명하게 된다.
확정 계획은 `docs/plans/2026-09-13-cut-first-and-plugin.md`.

### 비용 절감은 이유가 아니다 — 처음 주장은 틀렸다

초안은 "30% 자르면 STT도 30% 준다"고 적었다. **틀렸다.** 엔진은 이미 유일 소스마다
한 번만 전사한다(`speech.py:722`). 같은 소스를 두 번 쓰다가 인스턴스 하나를 지우면
타임라인은 줄어도 전사량은 그대로다. 게다가 아래 후보 검증 전사까지 붙으면 총량은
오늘과 대체로 비긴다. 우리가 사는 것은 **순서와 안전**이지 요금이 아니다.

### 무엇이 위험해지는가

`build_source_guard`는 보호 구간을 여섯 갈래에서 합집합하는데 **다섯이 전사에서
온다**(세그먼트·큐·재전사·경계 큐·불확실 커버리지). 컷을 먼저 하면 VAD만 남는다.
기준 명세도 못 박았다 — *"VAD는 확률적이다. 음성 손실 0을 보편적으로 주장하지 않는다."*

### 처음 쓴 안전 논증은 폐기한다

초안은 "두 단계 사이의 **사람 검토**가 전사 보호선보다 강하다"고 했다. **아니다.**

1. 편집본을 재생하는 것만으로는 **이미 사라진 대사를 발견할 수 없다.**
2. 더 나쁜 것은 순서다 — 오검출된 발화를 **먼저 영상에서 지우면**, 그 뒤 전사는 남은
   것만 듣기 때문에 **손실을 발견할 기회 자체가 없어진다.**

`InstanceGuard`의 비대칭도 정확히 봐야 한다: `status != "success"`는 `protected_frames`가
비어도 제거를 막지만, `status == "success"` + `protected == []`는 **제거 권한이 있다**.
"증거 없음"을 "보호 없음"으로 바꾸는 이 형태는 이 저장소에서 **다섯 번 재발했다**.

### 그래서 후보 검증 전사를 넣는다 (안전 수준 A)

```
VAD → 후보 블록(complement(guard) ∩ ≥6초 ∩ 적격)
    → 후보 블록만 전사해 확인
        · 글자가 나온다  → 그 블록 보호, 제거 취소
        · 글자가 없다    → vision 판정으로
        · 빈 응답 / 오류 → 보호 (빈 응답은 무음의 증거가 아니다 — D23)
```

**불변 방향: 전사는 보호만 더할 수 있고 제거 권한을 줄 수 없다.** 이 한 줄이
fail-safe를 구조로 만든다. 비용은 *제거 후보* 길이에만 비례하고, VAD가 이미 무음이라
본 구간이라 작다.

### 규칙 4를 여는 폭

레거시 전사 입력은 **그대로** `[0, duration]`을 빈틈없이 덮는다. 파생 계층만, 그것도
**명시적으로 선택된 타임라인 revision**의 가청 source 범위로 한정해 연다. 전사와
재전사는 그 요청 범위를 빠짐없이 처리하고, VAD·빈 응답·오류로 입력을 **더** 줄이지
않는다. D25가 막은 것("이 구간은 말이 아니다"라고 전사 계층이 판단하는 것)은 그대로
금지다 — 여기서 범위를 정하는 것은 **사용자의 타임라인**이지 모델의 판정이 아니다.

### 규칙 9는 완화가 아니라 별도 권한이다

초안은 *"제거된 구간은 영상 자체가 없으니 자막 손실이 아니다"*라고 정당화했다.
**부적절하다** — 위 2번 때문이다. 그래서 완화 대신 **감사 계약**을 요구한다:
파생 영상의 제거는 source/instance 범위·근거·실패 상태·복원 위치·**검토 상태**를 실은
`EditPlan`으로만 표현하고, 미처리·실패·경계 잘림을 빈 성공으로 바꾸지 않으며,
**자동 컷의 미검토 상태는 후속 자막 생성으로 해제되지 않는다.**

### 순서 역전이 부수로 요구하는 것 (재현으로 확인됨)

`gpt-6-astra` 방향 검토가 합성 호출로 직접 재현한 것들이다
(`docs/orchestration/reviews/astra-replan-cut-first.md`):

- **범위마다 엔진 전체를 독립 실행해야 한다.** 플래너만 부분화하면 떨어진
  `[10,11)`·`[40,41)`·`[70,71)`의 '치즈' 셋이 **61초짜리 되풀이 하나**로 묶이고 repair
  요청이 `[10,71)`이 된다 — 빼놓은 58초를 다시 듣는다. 검출기가 시간 간격을 보지 않고
  이웃을 묶기 때문이다(`repetition.py:124`, `repair.py:498`). refine도 간격을 넘어
  합친다(`refine.py:121`). **P4의 범위 국소 시계와 제한된 repair cutter가 이미 그
  물건이다** — 퇴역시키지 말고 재사용한다.
- **coverage 계약이 따로 필요하다.** `ChunkCoverage`는 "요청한 조각에 응답이 왔는지"만
  보고 "필요한 구간을 다 요청했는지"는 아무도 안 본다. 부분 trace가 미해결 표시 없이
  SRT를 만들고, 나중에 가드 증거로 재사용되면 미전사 영역이 **다시 무보호가 된다**.
  요청/완료/실패 범위를 구분하고 caption 완료 전에 필요 범위와 대조해야 한다.

### 확인하지 못한 것

희미한 발화·음악 아래 대사의 실제 VAD 검출률, 짧은 범위에서의 유료 whisper 품질과
청구량. 낮은 임계값·큰 패딩의 효과는 **실제 발화 손실 평가 전까지 주장할 수 없다.**

## D37 — 글자는 gpt-transcribe, 시각은 whisper-1 — 규칙 1·5 개정 (2026-09-16)

사용자 결정: **자막 글자를 gpt-transcribe로.** gpt-transcribe는 글자가 낫지만 세그먼트
시각을 주지 않는다. 단독으로는 SRT를 만들 수 없으므로 **하이브리드**다 — whisper-1의
`segments[]`가 시각과 세그먼트 경계를 그대로 주고, 글자만 그 세그먼트에 대응하는 gpt
글자로 갈아낀다(`vlogsrt/retext.py`, Q3-1). 방향 검토 둘(Opus UNSOUND, GLM
SOUND_WITH_CONCERNS)이 v1의 핵심 결함을 **독립 재현**했고, 이 결정은 그 v2다.

**이 기능의 정직한 이름은 "gpt-transcribe로 whisper 글자를 교정한다"이다.** whisper가
통째로 놓친 말은 되살리지 못한다 — 그 글자에는 시각이 없다. 기록(`trace.retext.unplaced`)에만
남는다.

### 새 권한 — 이것이 규칙 1·5를 연다

- **retext는 한글·영문·숫자를 바꾸고 지울 수 있다.** 조판 정리(D30)는 부호만 지운다.
  retext는 처음으로 출력 글자 자체를 바꾸는 계층이다. 그래서 규칙 1은 "시각과 세그먼트
  경계는 whisper에서만, 글자는 게이트를 통과한 세그먼트에서만 gpt에서"로, 규칙 5는
  "출력 글자를 바꾸는 곳은 retext·polish 둘"로 개정한다.
- **힌트·`keywords`가 이제 출하 글자에 영향을 준다.** 규칙 6은 그대로다 — whisper에는
  여전히 가지 않는다. 다만 검증 모델로 보내던 힌트가 SRT 글자를 바꿀 수 있게 됐다.
- **시각은 한 초도 바뀌지 않는다.** `retext.py`는 시각을 조각 배정과 되풀이 제외에만 읽는다.
  `spine_to_cues` 직후 큐의 개수·시각·`seg_ids`가 교정 on/off에 같다(테스트로 못 박았다).
  **refine 뒤 큐 개수는 같지 않다** — 글자 수가 분할 판정을 바꾼다(검토 A 재현: 1304 vs 1342).

### D24와 다른 점 — 셋 다 안전선이다

D24는 시각 없는 글자를 발화 구간에 **배분**하다 무너졌다. 같은 모양을 되풀이하지 않는다.

1. **시각을 배분하지 않는다.** whisper 세그먼트 경계를 gpt 글자열 위의 칸막이로 옮길 뿐이다.
   `replace` 블록 안에서는 글자 **위치** 비례로 나눈다 — 시간 비례가 아니다.
2. **세그먼트 사이에 낀 gpt 글자는 출력하지 않는다.** v1은 "삽입은 앞 세그먼트에 붙인다"였다.
   그 글자를 어느 세그먼트에 붙이는 순간 그 세그먼트의 시각을 준 것이다. 검토 A 실측:
   0.4초 세그먼트에 gpt 929자 → refine 후 412자·1.95초 큐, cps 884. 검토 B 합성: 조각
   유사도 0.91~0.98로 통과한 채 큐 하나에 82~165배.
3. **세그먼트 게이트.** 조각 게이트만으로는 부족하다(위 B 재현). 세그먼트마다 셋을 통과해야
   교체한다 — 일치율 하한, 길이 비 상한, 길이 비 하한(gpt가 말을 **지우는** 방향: A 재현에서
   한 조각이 gpt 7343자 대 whisper 9624자).

부수: 한 gpt 글자는 한 세그먼트에만 간다(칸막이). 불통과 세그먼트의 gpt 몫은 이웃에게도
가지 않는다 — 같은 말이 두 번 나가는 경로를 막는다. 정규화는 `strip_for_compare`와 같은
규칙(공백·부호 제거, casefold)이되 원문 위치 대응표를 유지해 **출력은 gpt 원문에서 자른다**
(부호 차이가 opcode를 35% 부풀린다 — 검토 B). 경계는 어절 경계로 스냅한다.

`SequenceMatcher`는 `말두번째말`처럼 같은 글자가 경계 양쪽에 있으면 세그먼트 사이의 삽입을
세그먼트 **안쪽**에 둔다. 정렬은 맞지만 사이의 말이 세그먼트 몫이 되어 멀쩡한 교정까지 막힌다.
삽입을 같은 글자 위로 미끄러뜨려 가장 가까운 경계에 붙인다(표준 diff의 slide). 글자 짝은
바뀌지 않는다 — 무작위 300회 칸막이 불변식 테스트가 지킨다.

### 두 번째 모델 호출의 소유

- 호출은 **`retext_enabled`에만** 의존한다. 검증 게이트(`if not verify_with_second_model`)
  **밖**, SRT 저장 **앞**. v1대로면 `--no-verify`가 교정을 조용히 끄고 SRT가 검증 플래그에
  따라 달라졌다(두 검토 공통).
- 검증은 같은 응답을 **재사용한다** — 같은 오디오에 두 번 결제하지 않는다.
- 불변식: **교정이 켜진 상태에서도 검증 on/off에 SRT 바이트가 같다.**
- 호출 실패·응답 없음 → 전부 whisper 글자 + WARN + `trace.retext.status = "unavailable"`.
  SRT는 막지 않는다.
- `--no-verify`의 "비용 절반"은 교정이 켜져 있으면 더 이상 사실이 아니다. 둘 다 꺼야 한 번만 낸다.

### 검증의 독립성은 retext 기록으로 옮겨 간다

검증은 **출력 큐**와 대조한다(검토 A 판정). whisper 기준 큐를 따로 `refine`하면 번호가
SRT와 어긋나고 refine을 두 번 돈다. 교체된 큐는 자명하게 일치하지만 **whisper로 남은 큐의
불일치가 곧 "교정하지 못한 자리"의 신호다.** 두 모델의 원래 차이는 `trace.retext.chunks[].similarity`
(교정 전 유사도)와 세그먼트별 불통과 사유가 담는다. `verify.py`는 바꾸지 않았다.

### 되풀이 구간 (검토 B 정밀화)

`Repair.outcome`이 `collapsed`·`kept`인 `Repair.span`과 **시간이 겹치는** 세그먼트는 교체하지
않는다(seg_id는 재전사가 다시 매기므로 키가 아니다). 그 자리의 gpt 글자 수를 WARN과 기록으로
남긴다 — "접힌 구간에 실제 발화가 있었을 수 있다"(규칙 9: 경고하고 계속). `replaced`는
재전사로 받은 새 whisper 글자라 교체를 허용한다(게이트는 그대로). `span`이 `(0.0, 0.0)`인
옛 기록은 되풀이 구간으로 대신 찾고 WARN한다.

### redo · trace

`TRACE_VERSION` 10.0. `trace.retext`에 상태, 조각별 유사도·게이트, **seg_id → 교체 글자 전체
매핑**, 불통과 사유, `unplaced`, 제외 구간과 gpt 글자 수가 실린다. `redo`는 이 매핑을 **그대로
다시 얹는다** — 안 하면 `vlogsrt redo`가 gpt 글자를 조용히 whisper로 되돌린다. `retext_*`를
바꿔 재계획하려면 두 번째 모델 응답이 필요하므로 `run`을 다시 돈다.

### 임계값 — 전부 잠정, 교체를 덜 하는 쪽

유일한 실데이터 `fr_day_1_2_fhd`는 **38분 조각 2개 + 규칙 6 이전 prompt로 녹화**돼(prompt
메아리 103회, 조각 유사도 0.59) 분포 근거가 못 된다. 합성 재현 시나리오에서 보수적으로 골랐다.
사람이 현재 설정(180초 조각)으로 재녹화하면 다시 정한다(`PENDING_HUMAN`).

|---|---|---|

### 파생 계층 — Q3-1에서는 whisper 전용

`project/speech.py`·`project/boundary.py`는 `pipeline.spine_to_cues`를 직접 부른다. 이 함수를
**whisper 글자 전용으로 고정**하고 교정은 엔진의 `pipeline.apply_retext`로 분리했다. 브리프는
필수 키워드 인자를 요구했지만, 기존 project 테스트의 spy가 `cues_spy(spine)` 한 인자만 받아
"project 테스트 무변경" 요구와 충돌한다 — 함수 분리로 둘 다 지켰다. 파생 계층은 오늘
gpt-transcribe를 **호출하지 않는다.**

**Q3-2가 파생 계층에서 켤 때 분석 키 버전을 올려야 한다.** 파생 계층 설정 지문은
`cfg.to_dict()` 전체 해시라 `retext_*`가 이미 들어간다 — 그러나 값이 같은 채 **동작만** 켜지면
옛 whisper 글자 완성물이 같은 키로 재사용된다. 그리고 Q3-2는 모든 소스 전사에 **새 유료
호출**을 더한다.

## D38 — 공백 없는 덩어리도 글자 비율로 자른다 — 줄 폭 16자 (2026-09-20)

실측 77분 회차 SRT에서 공백 없는 덩어리 두 줄이 화면 밖으로 나갔다(42번 `ㅋ`×56자,
265번 `ㅋ`×26자). 조판은 최대 `16자 + 56자`까지 내보냈다(S12). 원인은 두 층이 나란히
포기한 것이다 — `refine._char_split_index`는 공백이 없으면 `None`을 돌려 분할이 통째로
멈췄고, `layout.break_text`는 공백이 없으면 폭(16자)에서 **한 번만** 끊고 나머지를
둘째 줄에 전부 부었다. 어느 한 층만 고쳐도 안 된다. 분할만 고치면 33자 이상 조각이
여전히 넘치고, 줄바꿈만 고치면 32자를 넘는 큐를 두 줄에 담을 수 없다.

### 계약 — 임계값은 하나도 안 바꿨다

`max_chars_per_line = 16`, `max_lines = 2`(그래서 `max_chars_per_cue = 32`), `max_cps`,
`min_duration`, `max_split_depth` 모두 그대로다. 바뀐 것은 세 군데다.

1. **`refine._char_split_index`** — 공백이 없으면 같은 글자 비율의 유효한 내부
   인덱스를 돌려준다. `split_cue`의 나머지 계약(시각을 글자 수 비례로 나누고, 원본
   큐 구간을 벗어나지 않고, `max_split_depth`·`min_duration` 한도를 지키는 것)은 한
   줄도 안 바뀐다. `no_split_point`는 글자가 두 개 미만인 큐에만 남는다.
2. **`layout.break_text` 강제 분리** — `cut = min(max_chars_per_line, ⌈len(body)/2⌉)`.
   폭 한도는 그대로 지키면서 `16자 + 2자` 같은 외톨이 줄이 사라진다. 기존 30자
   입력은 `16/14`에서 `15/15`로 바뀐다. 공백이 있는 본문의 후보·점수 경로와 가운데
   균형은 그대로다.
3. **`pipeline._make_cues`** — 그래도 폭을 넘긴 줄이 남으면 줄 수를 담은 `WARN` 한
   줄을 남긴다. 큐 수가 아니라 줄 수를 센다. 조용히 넘기지 않는다(규칙 9).

### 16자는 목표 폭이지 절대 한도가 아니다

어절 경계 때문에 `17/14`가 되는 정상 문장을 두 큐로 쪼개 절대 한도로 만들지 않는다.
앞줄을 16자까지 채우는 방식은 실측 328개 2줄 큐 중 102개에서 둘째 줄이 4자 이하로
남고 2개는 3줄이 됐으므로 쓰지 않는다. 대표 결과: `ㅋ` 72자·6.8초 큐는 4장 `9/9`,
26자·1.86초(초당 글자수 초과)는 2장 13자, 20자·3.0초는 한 장 `10/10`, 어절 경계가 안
맞는 31자 문장은 한 장 `17/14` 유지.

### 기대값을 바꾼 테스트 한 건

`tests/test_refine.py::test_split_gives_up_on_a_single_long_word`는 `'가' * 40`이
한 장으로 남고 `no_split_point`가 붙는 것을 못 박았다 — 그 포기가 이번에 고친 결함
자체다. `test_split_cuts_a_single_long_word_in_half`로 이름과 기대값을 새 분할 계약에
맞게 바꿨다(두 조각 20자·20자, 플래그 없음). 단언을 삭제하거나 느슨하게 만들지
않았다.

### 실측 회귀

`fr_day_1_2_fhd.whisper.json`을 끝까지 처리한 결과(큐 1304장)는 수정 전후로
수·순서·시각·글자가 전부 같다. 이 픽스처의 골격에는 분할 계약이 바뀌어도 움직일
공백 없는 덩어리가 없다 — 화면 밖 줄을 만든 두 덩어리는 온라인 실행의 산물이라
오프라인 픽스처에 없다. 폭 초과 줄은 어절 경계 때문에 남는 1건(17자)뿐이고
`too_long` 표시가 붙어 있다.

## D39 — 파생 계층에도 글자 교정을 켠다 — 분석 키 v2 (2026-09-20, Q3-2)

D37(Q3-1)이 레거시 엔진에 넣은 글자 교정을 파생 계층(`project/speech.py`·
`project/boundary.py`)에 배선한다. 소스 전사와 경계 전사 모두 settle 뒤 큐 앞에서
두 번째 모델(gpt-transcribe)을 **1차 전사와 같은 조각 경계로** 다시 묻고
`retext.plan` → `pipeline.apply_retext` → `refine.refine` 순서로 얹는다 — 레거시
`pipeline._make_cues`와 같은 자리, 같은 순서다. 시각·경계·`seg_ids`·큐 수는 여전히
whisper 세그먼트 그대로이고, 게이트를 통과한 세그먼트의 글자만 갈아진다.

### 새 유료 호출

- 소스 분석 하나에 두 번째 모델 호출이 하나, 경계 요청 하나에도 하나씩 더해진다.
  조각이 같으므로 오디오 길이도 같다 — 전사 호출 비용이 대략 두 배가 되는 셈이다
  (되풀이 재전사·심판은 여기에 더해진다). 교정 호출은 되풀이가 없어도 **항상** 붙는다.
- `retext_enabled`가 거짓이면 아예 부르지 않는다(`switched_off`).
- 호출 실패는 **오류 기록이 아니라** `unavailable` 기록과 WARN이다 — whisper 글자로
  완성물이 나간다(D37과 같은 선). 재전사·심판·커터 실패가 타입 있는 error로 끝나는
  것과 다른 이유는 그 셋은 골격 신뢰를 깨뜨리지만 교정 실패는 골격을 하나도 고치지
  않았기 때문이다.
- 비용 추정기는 아직 없다(`inspect`는 P7-03의 계획) — 여기서는
  `docs/PROJECT_CONTRACTS.md` §9에 비용 성격만 적었다.

### 분석 키 v2 — 두 도메인을 함께 올린다

소스·경계 설정 지문은 `cfg.to_dict()` 전체 해시라 `retext_*`가 이미 들어 있다. 값이
그대로인 채 동작만 켜지면 **옛 whisper 글자 완성물이 같은 키로 재사용**된다. 그래서
`_SOURCE_KEY_DOMAIN`·`_BOUNDARY_KEY_DOMAIN`을 함께 v1→v2로 올렸다. 경계 캐시 키는
소스 분석 키를 재료로 쓰지만 도메인 자체가 그 분석의 의미를 말하므로 한쪽만 올리지
않는다.

### 기록 — `SourceTrace`·`BoundaryTranscript`의 선택 필드

`retext: RetextRecord | None = None`. 계획 전체(`texts` 매핑·불통과 사유·`unplaced`·

기록에서 사라지면 규칙 9 위반이다. 소스 `SourceTrace`는 직렬화 자체가 없으므로
메모리 기록으로만 남는다(기존과 같다).

이 때문에 같은 키의 재실행에서 교정 결과가 다르면(첫 실행은 두 번째 모델이 죽어

## D41 — Media Asset Protocol의 XPC 어댑터는 SDK에 자리가 없다. Apple event가 유일한 표면이다 (2026-09-21)

**문제**: 인수인계 기록이 남긴 다음 행동 하나가 "Workflow Extension SDK의 Media
Asset Protocol XPC adapter를 구현하거나 SDK 부재 근거를 기록함"이었다. 두 갈래
모두 전제가 확인된 적이 없었다 — SDK가 이 머신에 있는지도, 그 SDK에 자산 API가
있는지도 본 사람이 없었다.

**실측**: 둘 다 열어 봤다.

| 확인한 것 | 결과 |
|---|---|
| `/Library/Developer/SDKs/WorkflowExtensionSDK.sdk` | **있다.** `project.yml`의 `ADDITIONAL_SDKS`가 가리키는 그 경로다 |
| `usr/include/ProExtension/ProExtension.h` | 선언 하나뿐 — `ProExtensionHostSingleton()` |
| `Library/Frameworks/ProExtensionHost.framework/Headers` | `FCPXHost.h` · `ProExtensionHost.h` 둘. `Modules/module.modulemap` 있음 |
| `FCPXHost` 프로토콜 | `timeline` · `versionString` · `bundleIdentifier` · `name`. 전부 읽기 전용 |
| `FCPXTimeline` | `movePlayheadTo:` · `playheadTime` · `activeSequence` · `sequenceTimeRange` · 관찰자 등록 |
| `FCPXLibrary` · `FCPXEvent` · `FCPXProject` · `FCPXSequence` | 이름 · UID · URL · 시각. 전부 읽기 전용 속성 |
| 헤더 전체에서 `asset` · `xpc` · `media` 검색 | **0건.** `CMTime` import 두 줄이 전부다 |

**결정**: XPC 어댑터를 구현하지 않는다. 구현할 자리가 없다 — SDK가 노출하는
것은 활성 타임라인을 **읽고 재생헤드를 옮기는** 표면 하나이며, 자산을 만들거나
등록하는 API도, 그 용도의 XPC 서비스도 선언되어 있지 않다.

Apple이 자산 쪽에 정한 표면은 **Apple event와 SDEF**다. 이미 그 길로 구현되어
있다 — `macos/Resources/FinalCutAgent.sdef`가 `asset`을 클래스로, asset location ·
library location · data options를 속성으로, 자산 등록을 표준 `make` 명령으로
선언하고, `MediaAssetScripting.swift`가 `NSScriptCommand`와 KVC로 답한다.
`MediaAssetProtocol.swift`는 그 계약의 값과 검증만 소유한다.

**그래서 두 표면은 겹치지 않고 나뉜다.**

| 표면 | 무엇을 하나 | 어디에 |
|---|---|---|
| ProExtensionHost (`canImport` 안) | 활성 시퀀스·재생헤드를 읽고 옮긴다 | `WorkflowExtension/FinalCutTimelineBridge.swift` |
| Apple event · SDEF | 자산 위치를 답하고 `make`로 등록한다 | `FinalCutAgentCore/MediaAssetScripting.swift` |

**남는 것은 구현이 아니라 실기 확인이다.** KVC Apple event 계층은 빌드되고
단위 시험도 있지만, 실제 Final Cut이 이 응답을 받아들이는지는 서명된 앱으로
한 번 돌려봐야 안다. 그 확인이 끝나기 전에는 자산 표면을 "된다"고 적지 않는다.

**근거의 한계**: 위 표는 설치된 SDK(2024-10-30 배포분)와 Final Cut Pro
번들 안의 `ProExtensionHost.framework`를 읽은 결과다. Apple이 이후 배포에서
자산 API를 더할 가능성은 배제하지 않는다. 더해지면 이 결정을 다시 연다.

## D42 — 입력은 영상 파일에서 시작한다. 타임라인은 우리가 저작하고 합성 FCPXML로 건넨다 (2026-09-23, R-08)

**문제**: 파생 계층의 입구는 `parse_project` 하나였고, 받는 것은 Final Cut이
내보낸 FCPXML뿐이었다. 실물을 처음 넣어 보니 거부됐다.

```
ERR /fcpxml[1]/resources[1]/asset[1]:
소스/프로젝트 프레임 레이트가 다르다: 애셋 1001/30000초 ≠ 시퀀스 1/30초
```

29.97 DJI 클립 18개를 30p 프로젝트에 얹은 편집이었다. 거부는 세 자리에서
나지만 뿌리는 하나다 — 애셋 format, `asset-clip`의 format 오버라이드,
`conform-rate` 자식.

**그냥 30으로 진행하면 되는가 — 재어 봤다. 안 된다.**

Final Cut은 소스 프레임 하나를 타임라인 프레임 하나에 1:1로 얹어 놨다. 프레임
수는 보존되고 시간이 0.1% 줄어든다. 클립 안에서 그 오차가 누적된다.

| 클립 | 프레임 | 타임라인 | 소스 | 끝에서 어긋나는 양 |
|---|---|---|---|---|
| 1 | 1,168 | 38.9초 | 39.0초 | 0.04초 |
| 6 | 6,245 | 208.2초 | 208.4초 | 0.21초 |
| 11 | **40,730** | 1,357.7초 | 1,359.0초 | **1.36초** |

`min_gap`이 0.08초고 D33이 다룬 조판 밀림이 0.24초였다. 1.36초는 자막이 한
박자 늦게 뜨는 크기다. 리샘플링해서 받는 선택지는 여기서 닫힌다.

**결정**: 라이브러리·XML 입력을 제품 표면에서 내리고, **원본 영상 파일을 직접
받는다.** 받은 클립을 파일명 순서로 이어 붙인 **FCPXML 1.14를 합성**하고, 그것을
**기존 `parse_project`에 그대로 먹인다**. 문서를 손으로 조립하지 않는다.

합성한 뒤 파싱하는 우회를 고른 이유는 셋이다.

- `export.py`·`review.py`가 입력 `raw_xml`을 출력 템플릿으로 재사용한다. 합성
  XML이 있으면 출력 경로가 한 줄도 바뀌지 않는다.
- `fcpxml.py`의 거부 규율(격자·순서·겹침·소스 범위)이 **우리가 만든 것에도**
  그대로 걸린다. 합성물이라고 믿지 않는다.
- 사용자가 받을 산출물이 애초에 FCPXML이다. 입구와 출구가 같은 형식을 쓴다.

타임라인을 우리가 저작하므로 프레임 레이트 불일치·conform·lane·타이틀 같은
거부 사유가 **원천적으로 생기지 않는다**. 프레임 레이트가 섞인 묶음은 맞추지
않고 거부하며 어느 파일의 어떤 값이 다른지 이름으로 지목한다.

**CFR 증명은 패킷으로 한다.** `probe_video_stream`은 프레임을 전부 디코드해
증거를 모은다. 실측에서 4K HEVC 1,940프레임에 40초가 넘었고 75분 묶음이면
한 시간대가 된다 — 입력을 합성하려고 영상을 통째로 디코드할 수는 없다. 비디오
패킷은 프레임 하나에 하나씩 붙고 그 pts가 곧 제시 시각이라, 디먹싱만으로 같은
격자를 증명한다(실측: 40,730프레임이 1.4초). 증명 절차와 허용 오차는 프레임
경로와 **같은 함수**를 쓴다 — 다른 것은 증거의 출처뿐이다. 디코더가 실제로 그
프레임을 내는지까지 봐야 하는 프레임 표본 추출은 여전히 `probe_video_stream`을
쓴다.

**실측 인수** (클립 18개 · 4K HEVC 29.97 · 75분 13초):

| 확인한 것 | 결과 |
|---|---|
| `project receive --from-clips` | 종료 0, **22초** |
| 합성 문서 DTD 1.14 검증 | `valid=True`, `dtd_checked=True` |
| 두 번 합성한 `input.fcpxml` | **바이트 동일** |
| 시퀀스 길이 | 9026017/2000초 = 4513.0085초 |
| `project inspect` 비용 상한 | **$3.47** · 창 460개 · 이미지 2,760장 |

상한·창 수·이미지 수·길이가 **Final Cut export를 29.97로 고쳐 넣었을 때와 한
자리도 다르지 않다.** 합성 입력이 같은 분석 계획을 낳는다는 교차 확인이다.

**남은 것은 실기다.** 합성 FCPXML을 Final Cut이 실제로 가져오는지는 아직

**근거의 한계**: 위 수치는 DJI 클립 18개 한 묶음에서 나왔다. 색 좌표 표에 없는
입력, 프레임 레이트가 섞인 묶음, 비디오 스트림이 여럿인 컨테이너는 전부 거부로

오프라인 기본값이 이겼다. 사용자에게 「승인했는데 아무 일도 없다」로 보였다.

**결정**: `ui/app.py`는 dotenv를 읽기 **전에** 이 실행의 모드를 정한다.

- 인자가 없으면 **온라인**이다. `--offline`을 주면 그 실행의 유료 호출을 막는다.
- 온라인이어도 호출은 **영상·범위마다 견적 → 승인**을 거친다. 전체 라이브러리를
  자동으로 분석하지 않는다. 앞서 오프라인으로 실패한 선택은 로컬 견적만 되살리고
  유료 작업을 저절로 재개하지 않는다.
- 화면은 현재 프로세스 모드를 비밀 없이 표시한다(`raw/browser_runtime.py`).

**바뀌지 않는 것**: `pytest`·`vlogsrt run`·`vlogsrt record`·에이전트 작업의 규율은
그대로다. CLAUDE.md의 「`VLOGSRT_OFFLINE`을 0으로 바꾸지 마라 / `--online`을 쓰지
마라」는 **에이전트와 CLI**에 대한 금지다. 에이전트는 온라인 앱을 스스로 띄우거나
그 안에서 승인을 누르지 않는다 — 승인은 사람의 몫이다.

**근거**: `tests/raw/test_ui_entry.py`·`tests/raw/test_live_app_bootstrap.py`가
인자·dotenv 우선순위·파일 불변을 잡는다. 실제 유료 1회(영상 0014: 전사 1·Luna 2)는
사용자 승인 아래 성공했다(`docs/reports/2026-09-27-high-agency-implementation-feedback.md`).

## D45 — Final Cut과는 라이브러리 원본으로 들어와 타임라인 XML로 나간다. 플러그인은 없다 (2026-10-08)

**문제**: v2 계획(`docs/plans/2026-10-02-raw-video-browser-v2.md` §9.4)은 Final Cut
연결을 「확정 내보내기 폴더를 Finder에서 열어 사람이 가져온다」로 좁혔다. 실사용에서
사용자의 원본은 SD 카드가 아니라 이미 Final Cut 라이브러리 안에 있었고, 고른 컷을
다시 하나씩 끌어다 놓는 단계가 주 흐름의 병목이었다.

**결정**: 주 화면은 **라이브러리 불러오기 → 한 번 승인해 분석 → 사용/제외 검토 →
Final Cut 출력** 네 단계다.

- 입력: `.fcpbundle`을 **읽기만** 한다(`raw/fcp.py`). 이벤트의 `Original Media`를 기본
  역할로 고르고, 원본이 없을 때만 프록시를 쓰며 그 사실을 기록한다. 복사·검증은 기존
  A2 파이프라인(`ingest.run_ingest_copy`)이 한다. 끊어진 링크는 명시적 기록으로 남는다.
- 출력: 검증된 불변 패키지 옆에 **프레임 검사를 거친 타임라인 XML**을 만든다
  (`raw/final_cut_handoff.py`). 패키지의 core 범위만 spine에 오르고, 문서는 기존
  `clips.synthesize_fcpxml`로 합성한다(D42와 같은 길).
- Workflow Extension·플러그인은 되살리지 않는다(2026-10-02 사용자 지시 — 재설치 금지).

**지켜야 할 선**: 자동 정리(`raw/auto_cleanup.py`)의 제외 판정은 **사람이 사용/제외를
확정하기 전까지 미검토**여야 한다(D35). 지금 출력(`service.export_final_cut`)은 현재 검토
리비전에서 `selection == "included"`인 조각을 싣는다 — 자동 제외를 사람이 실제로 봤는지는
아직 증명하지 않는다. **열린 감사 항목**이다(TASKS W-5). `auto_cleanup.py`의
`SILENCE_SECONDS` 같은 모듈 상수도 규칙 8에 따라 설정으로 옮길 대상이다.

**남은 것은 실기다**: 출력 XML을 실제 Final Cut이 가져오는지, 원본 relink가 되는지는
확인하지 못했다(V3). 확인 전까지 이 경로의 인수는 합성 데이터 기준이다.
