# 성능 기준 측정 — 2026-11-13 (성능 계획 Phase 0, W-69 · D120)

계획: `docs/plans/2026-11-12-performance-optimization.md`. 이 보고서가 Phase 0의 DoD다 — 계획의 순위를 실측으로 다시 매긴다.

## 대상과 방법

- **기계**: Apple M1 Pro(P 8 + E 2) · 32 GB · ffmpeg-full 9.0.2. 오프라인(유료 호출 0).
- **작업공간**: 사용자의 실제 작업공간 `~/Movies/namdang/_vlogsrt`(원본 169개)의 **사본**.
  - `export/`(3.7 GB)는 빼고 복사했다(1.4 GB). DB는 `sqlite3 .backup`으로 떴다.
  - 원본 영상은 원래 폴더를 읽기만 한다(미디어 경로는 작업공간 상대 경로라 사본이 원본 작업공간을 건드리지 않는다).
  - 원본 작업공간 DB의 mtime은 그대로다. 백업 명령이 원본 옆에 빈 `-wal`과 `-shm`을 남겼다(앱이 다음에 열 때 SQLite가 정리한다).
- **UI**: `scripts/bench_workbench.py --workspace <사본>`(각 ×5, 시간은 프로파일 **없이** 잰 실행). 그 앞 실행에서
  `--profile`로 뜨거운 자리만 찾았다(이 bench는 그사이 `status_tick` 인자 수가 바뀌어 틱 단계에서 죽고 있었다 — 고쳤다).
- **외부 프로세스**: 새 경과 시간 기록(`preprocess.process_step_totals`, D120)을 bench 끝에 찍었다.
- **작업 이력**: `scripts/perf_baseline.py --workspace <사본>` — DB만 읽는다(`mode=ro`).
  - `jobs`는 만든 시각·마지막 갱신뿐이라 **줄 서서 기다린 시간이 섞인다**. 그래서 같은 종류가 60초 안에 이어 걸린 작업을 한
    묶음으로 보고 묶음의 벽시계를 잰다.

## 2. 카드 누르기 뒤의 배경 작업 — 가장 큰 낭비

카드 누르기 5번(bench)이 건 배경 작업(`show_cached` → `publish_selection_review` → `plan_segmentation_from_analysis`
→ `_measured_source`)이 라이브러리 **전체 169개**의 시계를 다시 쟀다.

| 단계 · 도구 | 수 | 합(초) | 평균(초) | 최대(초) |
|---|---:|---:|---:|---:|
| 추출 시계 확인 · ffprobe(패킷 스캔) | 2530 | 344.4 | 0.14 | 0.5 |
| 원본 확인 · ffprobe | 2535 | 333.0 | 0.13 | 0.5 |

- 누를 때마다 원본 169개 × ffprobe 둘 ≈ 1000번이고, 프로세스 시간으로 **약 135초**다.
- 원인: 원본 조사 기억(`PROBE_MEMO.entries = 128`, W-45)이 「원본 60개쯤」에 맞춰져 있다. 원본 169개는 조사·시계 두 칸씩
  338칸이 필요해 LRU가 한 바퀴마다 전부 밀려난다 — 기억이 한 번도 맞지 않는다.
- 이 작업은 로컬 미디어 자리 밖에서 돌아 분석·미리보기와 CPU를 다툰다.

## 4. `Server-Timing`의 한계

미들웨어가 모든 응답에 `Server-Timing: app;dur=…`을 단다(D120). 그러나 그라디오 이벤트 결과(1.46 MB 그리기)는 큐의 이벤트
흐름으로 가므로 여기에 보이지 않는다 — 보이는 것은 `/media`·`/vl-activity`·글꼴 같은 그 밖의 경로의 응답 머리까지다.
그리기 비용은 위 bench가 잰다.

## 6. Rust 전환 조사 측정 (2026-11-18)

Rust로 다시 쓰면 얼마나 빨라지나를 가르려고 순수 Python 구간을 따로 쟀다(M1 Pro · 오프라인 · `scratchpad` 스크립트, 저장소 밖).

| 구간 | 실측 | 그 안의 Python 몫 |
|---|---|---|
| VAD 창 하나(512표본) | 정규화 22 µs · `asarray` 11 µs · onnx 115 µs · 상태 검사 22 µs | 32% — 스테레오 오디오 1분에 0.63초 중 0.20초 |
| 표본 대조(원본 하나, 20초 창 셋) | 포락선 26 ms × 2 · 상관 69 ms(지연 201 × 2000칸) | 약 0.36초 전부 — PCM sha로 캐시, 배경 작업 |
| 작업대 그리기(합성 원본 18개) | 중앙 58 ms(원본마다 약 3 ms) | 퍼져 있다 — 한 번에 JSON 디코드 약 240 · 파일 열기 약 200 · SQLite 실행 96 · `stat`/`lstat` 약 2700(경로 풀기) · `Fraction` 생성 약 5200 |

- 그리기 프로파일의 누적 상위: 원본마다 등급 보고서(`_tier_report_for_row`) — 자막 시각 확인 보고서를 원본마다 두 번 읽고(`current_report`) 1단계 오디오(`stage1_audio`)·
  남긴 구간(`kept_ranges`)을 그릴 때마다 다시 짓는다. 그리기 사이에 바뀌지 않은 파일을 다시 읽고 푸는 일이 가장 크다 — 언어가 아니라 기억(파일 mtime·크기 열쇠)의 문제다.
- `bench_workbench.py`의 1초 상태 틱 인자를 지금 모양(`status_tick(signature, mode_shown, *sent)`)으로 고쳤다 — 범위 칸 둘이 빠진 뒤로 그 단계에서 죽고 있었다.
